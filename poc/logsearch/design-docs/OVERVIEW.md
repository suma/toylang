# OVERVIEW — 何を作り、何を作らないか

## 1. 目的

`logsearch` は、**toylang で書かれた常駐サーバの実例**である。目的は 2 つある。

1. **道具として使えること** — 1 台のホスト (あるいは小さなクラスタの
   収集ノード 1 台) のログを集め、数日〜数週間ぶんを保持し、
   「昨日の 14 時台の `app=api` で `timeout` を含む行」を秒で引けること。
2. **言語のモデルケースであること** — ネットワーク I/O、ファイル I/O、
   自前のバイナリ形式、圧縮、索引、イベントループ、常駐プロセスの
   メモリ規律という、**実アプリが踏むものを一通り踏む**こと。
   踏んで痛かった箇所は [`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) に貯める。

2 番目は飾りではない。既存の example (`net_echo_server.t` など) は
どれも「1 つの機能が動く」ことを示すもので、**機能を組み合わせたときに
初めて出る問題** — 常駐プロセスのメモリ、複数ファイルへの分割、
バイナリ形式の相互運用 — は誰も踏んでいない。

## 2. 想定規模 (設計が壊れない範囲)

数字は「ここまでは設計上支えるつもり」という宣言であって、測定値ではない。
実測はベンチを取った時点で置き換える (現に取れたぶんは
[`ROADMAP.md`](ROADMAP.md) §2 と [`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) §0 にある)。

| 項目 | 目標値 | 効いてくる場所 |
|---|---|---|
| 取り込み速度 | 5,000 行/秒 (平均 200 バイト/行 = 約 1 MB/s) | イベントループの 1 周の予算 |
| 1 レコード最大長 | 64 KiB | 受信バッファの上限 |
| アクティブセグメント | 8 MiB (満杯か 60 秒でフラッシュ) | 常駐メモリの主要因 |
| 保持量 | 1 マウントあたり 100 GiB / 全体で 8 マウント | カタログの行数 (〜10 万 × 64 B) |
| 同時接続 | 128 (収集 + 検索の合計) | 接続テーブルの静的確保 |
| クエリ応答 | 1 日ぶん (〜50 GB) の語句検索で 2 秒以内 | セグメント枝刈りと語彙索引 |
| 常駐 RSS | 定常で 256 MiB 以下、**時間とともに増えないこと** | [`MEMORY.md`](MEMORY.md) |

最後の行が一番重い要件である。他は遅ければ遅いなりに動くが、RSS が
単調増加するサーバは**動かないのと同じ**なので、これだけは回帰テストで
縛る ([`ROADMAP.md`](ROADMAP.md) §4 の「定常性」)。

## 3. スコープ

### やる

- **収集**: TCP 行プロトコル (1 行 1 レコード) と `POST /v1/ingest`
- **構造化**: 行の先頭に付いた `key=value` 列をラベルとして取り出し、残りを本文とする
- **保存**: 不変セグメント、再構築できるカタログ、複数マウントへの配置
- **圧縮**: フレーム単位の自前コーデック (`LSZ1`) と、冷えたセグメントの
  アーカイブへの併合
- **索引**: セグメントごとの時刻範囲、ラベル辞書、語彙索引 (転置)
- **検索**: 時刻範囲 / ラベル一致 / 語句一致 / 本文部分一致、時刻順の並べ替え、
  カーソルによるページング
- **API**: HTTP/1.1 の部分集合を話すサーバ、NDJSON と JSON のレスポンス、
  1 枚の HTML で完結する検索 UI
- **運用**: 統計エンドポイント、明示フラッシュ、クリーンな停止

### やらない (この設計の非目標)

| 非目標 | 理由 |
|---|---|
| 分散・レプリケーション・クラスタリング | 1 プロセスで完結させる。合意も再配置も範囲外 |
| TLS / 認証 / 認可 | 暗号ライブラリが無い。**信頼できるネットワークに置く**前提とし、公開するなら前段に reverse proxy を置く (README ではなく運用文書の責務) |
| 正規表現 | エンジンを書く費用が索引の費用を上回る。部分一致 (`contains`) と語句一致で代替する |
| 時系列グラフ・アラート | 検索が先。`top=` の集計までは入れた ([`QUERY.md`](QUERY.md))、それ以上は後 |
| gzip / zstd 互換のアーカイブ | 互換形式は Huffman + CRC + ヘッダの完全一致が要る。**自分で書いて自分で読む**形式に倒し、標準ツールで開きたい要求は「エクスポート機能」として後段に置く ([`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) の G7) |
| ログの改変・削除 API | 追記のみのストアにする。保持期限が来たセグメントは**サービス自身が丸ごと消す** ([`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) §8) が、行単位の削除・訂正は持たない |
| syslog RFC 5424 / RFC 3164 の完全実装 | 優先度・タイムスタンプ・ホスト名の抽出だけ行い、構造化データ部は本文に残す |

## 4. 用語

この設計で一貫して使う語。**同義語を混ぜない**ために先に固定する。

| 語 | 意味 |
|---|---|
| **レコード (record)** | ログ 1 行。`(ts, seq, labels, body)` の 4 つ組 |
| **`ts`** | レコードの秒精度 UTC 時刻。行から読めたらそれ、読めなければ受信時刻 |
| **`seq`** | プロセス起動から単調増加する u64。`ts` が同秒のレコードの順序を決める。**`(ts, seq)` がレコードの全順序であり、カーソルの正体**でもある |
| **ラベル (label)** | `key=value` の組。`host` / `app` / `level` など。値は辞書符号化される |
| **本文 (body)** | ラベルを取り除いた残りのバイト列。検索対象の主 |
| **ストリーム (stream)** | ラベル集合が同一のレコードの並び。セグメント内の物理的なまとまりでもある |
| **セグメント (segment)** | 不変のファイル 1 本 (`.seg`)。本文と索引を同じファイルに持ち、書き終わったら二度と変わらない |
| **フレーム (frame)** | セグメント内の圧縮単位。既定 256 KiB (非圧縮時) |
| **アーカイブ (archive)** | 冷えたセグメントを併合した大きなセグメント。形式は同じで、粒度だけが違う |
| **マウント (mount)** | 保存先ディレクトリ 1 つ。設定ファイルで宣言する。物理ディスクとは 1:1 とは限らない |
| **カタログ (catalog)** | マウントごとの目録 (`meta/catalog.<gen>.snap` + ジャーナル)。**真実はディレクトリの方にあり、カタログはそれを速く読むためのキャッシュ**で、いつでも作り直せる |
| **全体カタログ** | 全マウントのカタログをメモリ上で束ねたもの。枝刈りはここで行う。永続しない |
| **アクティブセグメント** | まだディスクに出ていない、メモリ上の書きかけセグメント |

## 5. 設計の指針

repo 全体の流儀に合わせ、この設計も次の順で判断する。

1. **今日動く形を選ぶ** — 言語に無い機能を前提にした設計は書かない。
   足りないものは [`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) に「無くても回る回避策」
   とセットで書く。回避策が書けないものだけが本当の前提条件 (R 項目) になる。
2. **却下した案を残す** — なぜその形なのかは、選ばなかった形と並べないと伝わらない。
3. **観測できることを設計に含める** — 統計・`--profile=mem`・契約
   (`ensures allocates(N)`) は後付けではなく最初から置く。**サーバの正しさは
   「落ちない」ではなく「定常である」**なので、定常であることを測る手段が要る。
