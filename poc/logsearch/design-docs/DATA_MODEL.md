# DATA_MODEL — レコードからマウントまで

## 1. レコード

```rust
# One log line, after parsing. `labels` indexes into the segment's
# label dictionary, so a record never owns a string.
struct Record {
    ts: u64,          # UNIX nanoseconds (epoch is UTC by definition)
    seq: u64,         # process-monotonic tie-breaker
    stream: u32,      # index into the segment's stream table
    body_off: u32,    # offset into the segment's body arena
    body_len: u32,
    flags: u32,       # truncated / parse-failed / ...
}
```

**レコードは文字列を持たない。** これは美観ではなくメモリ規律である
([`MEMORY.md`](MEMORY.md)): 1 レコードが `String` を 2 つ持つと、
1 秒 5,000 行で 1 日 8.6 億回の確保になり、**返ってこないヒープ**では
そのまま RSS になる。ラベルは辞書の符号 (u32)、本文はアリーナ内の
オフセットにする。

### `(ts, seq)` が全順序

`time::now_unix_ns()` が **UNIX epoch からのナノ秒**を返す
(`core/std/time.t`)。それでも `seq` を第 2 キーに
残すのは、**取り込みは 1 バッチで時刻を 1 回しか読まない**からで、
同じ ns を持つレコードが束で現れる。**`(ts, seq)` をレコードの全順序と
定義する**。この組はそのまま:

- セグメント内の物理順 (常に昇順で書く)
- クエリのカーソル (`?cursor=<ts>.<seq>`)
- ページングの再開点

になる。オフセット (`LIMIT ... OFFSET`) 方式を採らないのはこのためで、
取り込みが進むとオフセットは意味を失うが、`(ts, seq)` は不変である。

> **`seq` は再起動でリセットされる。** `ts` が先に比較されるので順序は
> 壊れない。ns 精度になったので、再起動を跨いで同じ `ts` が出る確率は
> 実質ゼロになり、v1 で残していた「同一秒に再起動すると順序が未規定」
> という穴は消えた。

## 2. ラベルと本文

取り込み時に、行の先頭から連続する `key=value` トークンをラベルとして
剥がし、残りを本文とする。

```
2026-09-03T12:00:01Z host=web01 app=api level=error request timed out after 30s
└─ 時刻 ────────────┘└─ labels ─────────────────────┘└─ body ──────────────────┘
```

規則は 3 つだけ。

1. **先頭からの連続した `key=value` だけがラベル**。本文中の `=` は本文のまま
   (`timeout=30s` が本文の途中にあってもラベルにはならない)。
2. **`key` は `[a-z0-9_]{1,32}`**。それ以外に当たったらラベルの走査を止める。
3. **`value` は空白まで**。引用符は解釈しない。値に空白を入れたければ
   ラベルではなく本文へ書く。

引用符もエスケープも入れないのは、パーサが状態機械 1 つで済むからである。
**構造化ログの完全な形式 (logfmt / JSON) を受けたい要求は、
取り込み経路を足す形で解く** — 中心のデータモデルを複雑にしない。

### 予約ラベル

| ラベル | 意味 | 既定 |
|---|---|---|
| `host` | 送信元ホスト | 接続の peer アドレス |
| `app` | アプリ名 | `unknown` |
| `level` | `debug` / `info` / `warn` / `error` / `fatal` | `info` |
| `truncated` | 64 KiB を超えて切られた | 付かない |

`level` だけは順序を持つ (`debug < info < warn < error < fatal`) ので、
クエリで `level>=warn` と書ける。他のラベルは等値と集合 (`in`) だけ。

## 3. ストリーム

**ラベル集合が完全に一致するレコードの並び**をストリームと呼ぶ。
セグメントの中では、レコードはまずストリームごとにまとめられ、
その中で `(ts, seq)` 昇順に並ぶ。

これは圧縮率のための配置である。同じストリームの行は語彙がほぼ同じなので、
LZ77 の窓 (64 KiB) の中に似た文字列が並び、マッチが長くなる。ホスト混在の
時系列順に並べた場合と比べて、同じデータで圧縮後サイズが目に見えて変わる
はずの箇所であり、**ベンチで測る対象**でもある。

代償として、セグメント内は時刻順ではなくなる。クエリはストリームごとの
昇順ランを **k-way merge** で束ねて時刻順に戻す (`PriorityQueue<T: Ord>` が
そのまま使える。[`QUERY.md`](QUERY.md) §4)。

## 4. セグメント

**セグメントは書き終わったら二度と変わらない。** この 1 行から以下が従う。

- 索引はセグメント作成時に完成する (後から足さない)
- 更新も削除も無いので、読み手は排他を考えなくてよい
- 保持期限は「セグメント単位で捨てる」しか無い。**行単位の削除は無い**

| 性質 | 値 |
|---|---|
| 目標サイズ | 8 MiB (非圧縮のレコード本文の合計)。上限ではなく選択 ([`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) §0) |
| フラッシュ条件 | 目標サイズに達した / 60 秒経過 / 明示フラッシュ / 停止 |
| ファイル | `<mount>/seg/YYYY/MM/DD/<segid>.seg` (本体 + 索引、日付は `ts_min` の UTC) |
| `segid` | 12 桁ゼロ詰めの u64。**マウントを跨いで一意** |

`segid` はグローバルなカウンタで、マウントを跨いで一意にする。マウントを
跨いだ移動 (マウント間のリバランス) をしてもファイル名が衝突しないためで、
**カタログのキーが `(mount, segid)` ではなく `segid` だけで済む**のが利点。

## 5. アーカイブ

冷えたセグメント (既定: 24 時間以上前) を、同じストリーム構成のまま
**併合して 1 本の大きなセグメントにする**。形式はセグメントとまったく同じで、
違うのは粒度だけ。名前は `<segid>.arc.seg` で、`segid` は
併合結果に新しく振る。

併合が得るもの:

- **圧縮率** — 8 MiB の窓を跨いで似た行が並ぶ
- **枝刈りの速さ** — カタログの行数が 1/32 になる (256 MiB 単位に併合)
- **開くファイル数** — 1 クエリが触るファイルが減る

失うもの: 併合の間だけディスクを二重に使うこと。**併合が終わったら元の
セグメントは消す** (`fs::remove_file`、[`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) §8)。

**2026-09-21 に landing** (`src/compact.t`、`compact` サブコマンドと
`POST /v1/admin/compact`)。レコードは**読み直して再投入する** —
セクションごとに繋ぐと語彙・リンク・ストリーム表・フレーム配置の
4 つを併合規則ごと書くことになるが、`ArchiveWriter::add` に通せば
取り込みと同じ 1 本の経路が全部を引き受ける。代償は行をもう一度
パースすることで、対象は定義上冷えたファイルである。
**出力が台帳に載ってから入力を消す**ので、途中で落ちれば両方残る
(無駄だが正しい)。逆順なら失う。

## 6. マウント

保存先ディレクトリ 1 つ。**設定ファイルで宣言する**もので、探索はしない
(`fs::list_dir` はあるが、**勝手に見つけたディレクトリに書くべきではない**。
以前ここには「`readdir` が無い」と書いてあったが、それは 2026-09-03 に
`core/std/fs.t` が入って消えた理由である)。

```
# logsearch.conf
mount /var/log/logsearch/a  quota=100G
mount /mnt/disk2/logsearch  quota=400G
mount /mnt/disk3/logsearch  quota=400G  readonly
```

| 属性 | 意味 |
|---|---|
| `quota` | このマウントに書いてよい総バイト数。**実際の空き容量ではなく宣言値** (`statfs` が無いので実測できない) |
| `readonly` | 読むだけ。過去データを載せた退避ディスクを繋ぐときに使う |
| 状態 | `active` / `full` (quota 到達) / `degraded` (書き込み失敗) |

### 配置ポリシー

新しいセグメントを書くマウントは、`active` なマウントのうち
**「使用率 (`used / quota`) が最小のもの」**を選ぶ。同率なら宣言順。

- `used` は**自分のカタログの合計**であって `df` ではない。`fs::file_size` で
  自分が書いた分は実測できるようになったが、他のプロセスが同じディスクを
  食っていても検知できない (`statfs` が無い、
  [`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) G4)。
- ラウンドロビンではなく使用率にしたのは、**容量の違うディスクを混ぜる**のが
  普通だから (100G と 400G を交互に使うと小さい方が先に埋まる)。
- ハッシュによる決定的配置 (`segid % n`) は**採らない**。マウントを足したときに
  既存データの所在が変わってしまい、探索できない環境ではそれが致命的になる。
  **どのファイルがどこにあるかはカタログが答える — そしてカタログが
  壊れたらディレクトリが答える** ([`STORAGE_FORMAT.md`](STORAGE_FORMAT.md)
  §7 の `--repair`)。

### 1 マウント = 1 カタログ

マウントは自己完結する。あるマウントのディレクトリを丸ごと別ホストへ
コピーしても、そこにあるセグメントは**そのマウントの `meta/` だけで読める**。
全マウントを束ねたカタログはメモリ上にしか存在せず、どこにも永続しない。

これは「壊れたときに何を捨てられるか」を単純にする: マウント 1 つが
死んでも、他のマウントは無傷で読める。中央のインデックスを 1 つ持つ設計は、
それが壊れると全部が読めなくなる。**そしてマウント内のカタログも
キャッシュでしかない** — 捨てれば `seg/` を歩いて作り直せる。
