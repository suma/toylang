# ONTOLOGY — 行から実体へ

> 状態: **O0 / O1 landing 済み**。`src/extract.t` が行からフィールドを取り出し、
> `.seg` の語彙索引 (kind=6) とリンク (kind=7) がそれを引ける形にしている。
> 前提: [`QUERY.md`](QUERY.md) (クエリの構文)、
> [`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) (索引の置き場所)、
> [`DATA_MODEL.md`](DATA_MODEL.md) (レコードとラベル)。
> 数値はすべて `poc/logsearch/log/apache2` の 181,519 行 (30.5 MB) に対する実測。

## 1. Palantir から何を借りて、何を借りないか

Foundry の Ontology は、データの物理形式とは別に置く**意味層**である。

| 要素 | 中身 | ここでは |
|---|---|---|
| **オブジェクト型** | 実体。主キーとプロパティを持つ | **借りる** (§2) |
| **リンク型** | オブジェクト間の関係。辿れることが価値 | **借りる** (§4) |
| **アクション** | オブジェクトへの書き戻し | **借りない** — アーカイブは不変 |
| **関数** | オブジェクト集合への型付きロジック | **借りない** — 今の「積」で足りる |
| データセット → オブジェクトの**マッピング層** | パイプラインが変わっても語彙が変わらない | **借りない** — ソース 1 台では定義言語の維持費だけが残る |

Ontology が効くのは**多数のソースと多数のチームが同じ語彙を共有するとき**で、
このサービスの規模ではない。借りるのは上 2 つだけにする。

## 2. なぜ入れたか — 部分一致は数として信用できない

| 数え方 | `404` の件数 |
|---|---|
| 部分一致 (`grep -c` と一致) | 55,599 |
| HTTP のステータスが実際に 404 | **53,689** |

**1,910 行 (3.4%) は誤爆**である。応答バイト数や IP やパスの中の `404` を
拾っている。取りこぼしはゼロなので精度 96.6% / 再現率 100% —
「だいたい合っているが数として信用できない」という最も扱いにくい状態だった。

`404 /wp-login.php` では 409 件に対し真値 208 件で、**半分が誤爆**だった。

## 3. オブジェクト型と抽出 (`src/extract.t`)

行の中に素材はすべてある。**framing** (`record.t`: 時刻・host・tag・本文の境界)
と **抽出** (`extract.t`: フィールドの意味) を分けてあり、形式を足すときに
触るのは後者だけになる。

| 型 | 主キー | プロパティ | 出どころ |
|---|---|---|---|
| `HttpRequest` | (segment, ordinal) | `ip` / `vhost` / `method` / `path` / `status` / `bytes` / `referer` / `ua` | apache access |
| `ClientIp` | アドレス | — | apache の client フィールド |
| `Host` / `Service` | ホスト名 / タグ | — | syslog |
| `FirewallBlock` | (segment, ordinal) | `K=V` の各値 | kern.log の `[UFW BLOCK]` |

### 抽出器は 1 つの形を仮定してはいけない

同じディレクトリに 2 つの書式が混ざっている:

```
173,165 行   1.2.3.4 - - [...] "GET / HTTP/1.1" 200 11103 "-" "..."
  6,682 行   blog.example:80 1.2.3.4 - - [...] "GET /robots.txt ..." 301 612 "-" "..."
```

第 1 フィールドを client と決め打つと 6,682 件が
`blog.obfuscatism.net:80` という名前の「IP」になる。**タイムスタンプの `[` を
軸に、その前のトークン数 (3 なら vhost なし、4 ならあり) で判別する。**

### 抽出の答えは厳密オラクルと一致する

| フィールド | エンジン | 検算 |
|---|---|---|
| `status` | 200:77,578 / 404:53,689 / 301:34,810 / 400:6,105 / 304:4,979 / 206:1,582 | 全一致 |
| `method` | GET 162,320 / HEAD 6,839 / POST 4,342 / `\x16\x03…` 4,202 / CONNECT 569 | 全一致 |
| `ip` | 127.0.0.1 3,410 / 52.139.44.162 3,260 | 全一致 |
| `vhost` | blog.obfuscatism.net:80 が 6,682、他はゼロ | 全一致 |
| フィールドを持たない行 | 1,672 | オラクルの「パース不能」と同数 |

**`method` の 4 位は TLS ハンドシェイク** (`\x16\x03\x01…` が 4,202 件) —
HTTPS を平文ポートに投げたクライアントで、部分一致では決して見えない。

## 4. 語彙索引 (セクション kind=6)

索引の語を**キー付き**にする。それだけで 3 つが同時に手に入る。

```
status:404      ip:127.0.0.1      path:/wp-login.php
method:GET      vhost:blog.example    ua:Mozilla/5.0 (…)      host:web01    tag:CRON
```

1. **誤爆が消える** — `status:404` はバイト数の `404` と別の語
2. **集計が索引の副産物になる** — 語ごとに `doc_count` を持つので、
   上位 N は postings を読まずに出る
3. **保存構造を足さずに済む** — セクション表は「知らない kind は飛ばす」形

### 形式

```
term_count: u32
for each term: name_len: varint, name bytes          # 出現順
for each term: doc_count: varint, post_off: varint, post_len: varint
postings_blob: 語ごとに delta-varint の昇順 ordinal 列
```

セクション全体を `"LST1"` フレーム (codec / 生長 / 圧縮長 / CRC) で包み、
**LSZ1 で圧縮する**。語の名前はパス由来で重複だらけなので自前のコーデックが
そのまま効く。

**語は辞書順ではなく出現順**である。設計は二分探索のために辞書順を求めたが、
2 万語の文字列ソートは `Vec::sort` (挿入ソート) を通ることになり二乗になる。
読み手が 1 パスで表を作るので完全一致は無影響で、**先送りしたのは前方一致**。

### 効き方

| | 索引 | 合計 | 索引の追加ぶん | `status` の集計 |
|---|---|---|---|---|
| 索引なし | 2.97 MB | 7.16 MB | — | 286 ms (全走査) |
| 索引・無圧縮 | 6.35 MB | 10.54 MB | +47% | **2 ms** |
| 索引・LSZ1 | 4.40 MB | 8.59 MB | **+20.0%** | 36 ms |

種類が少ないフィールドほど効く (`status` は 16 語で 143x、`path` は
2 万語で 2.6x)。**distinct が多い列の集計は distinct に比例する**という
当たり前の性質で、それ以上を望むなら索引側に上位 N を持たせるしかない。

## 5. リンクと traversal (セクション kind=7)

**同じレコードに現れた 2 つのフィールド値の組**を、書き出しの時点で数える。

```
ip → path      ip → status     ip → ua
path → status  path → ip       vhost → path     host → tag
```

**全組合せは張らない** — 6 フィールドなら順序つきで 30 組になり、
問いたい形はその中の数本しかない。

```
$ logread query <arc> "ip=127.0.0.1 top=path limit=5"
linked path for ip:127.0.0.1
  48  /
   8  /.env.production.local
   8  /%252eaws/config
   8  /env
   7  /.env~
segments 2 hold this value   link rows 2427   distinct 1908   elapsed 47 ms
```

**フレームを 1 つも展開しない。** 答えは検算と一致する (異なるパス 1,908 対
オラクル 1,909 — 差の 1 件は**空のパス**で、空の値は語にしない規約どおり)。
そして読んで意味がある: 上位が `/` の次に `.env` 系で、**資格情報を漁る
スキャナ**だと一目で分かる。

費用は索引が 4.40 → 4.93 MB (+12%)、書き出しが 719 → 781 ms
(いずれも v2 での実測。v3 で 1 ファイルになっても中身は同じ)。

## 6. クエリからの見え方

構文の正本は [`QUERY.md`](QUERY.md)。オントロジーが足したのは 2 つ。

- **`key=value` のうち索引が知っているキー** (`status` / `method` / `path` /
  `ip` / `vhost` / `ua` / `host` / `tag`) は postings で解決し、
  **語が無いセグメントは展開しない**。それ以外のトークンは今までどおり本文の部分一致
- **`top=<field>`** は行ではなく値を返す。**フィルタと組み合わせると
  traversal になる** (`ip=X top=path`)

**フィールドは完全一致である。** `ua=MJ12bot` は 0 件になる (語は user agent
の全体)。黙って 0 件を返さず「フィールドは値の全体に一致する」と言う。
部分一致で探すなら `MJ12bot` と書けばよい。

## 7. 借りないもの

| 借りないもの | 理由 |
|---|---|
| 汎用のマッピング層 | ソースが 1 台では定義言語の維持費だけが残る。**抽出器はコードで書き、形式の追加はコードの追加** |
| アクション (書き戻し) | アーカイブは不変。入れるなら注釈オーバーレイを別ストアに置く形になる |
| プロパティ単位のアクセス制御 | 認証機構自体を持たない ([`OVERVIEW.md`](OVERVIEW.md) の非目標) |
| オブジェクト集合の汎用クエリ言語 | 今の「積」で足りる。括弧も OR も否定も、実際に困ってから |
| オブジェクトのバージョニング | ログは追記のみで、実体の履歴はイベントの列そのもの |

## 8. 実装で分かったこと

**外部オラクルを名指すときは、そのオラクル自身をまず疑う。**
`status` の分布を `awk '{print $9}'` で数えて `400` を 835 件としたが、
真値は 6,105 件だった — リクエスト行が壊れている行でフィールド位置がずれる。
エスケープを踏まえた正規表現に替えて初めて突き合わせられた。

**`\"` を読めないと、攻撃の payload がステータスになる。** apache は
リクエストと UA の中の `"` を `\"` と書く。最初の実装は最初の `"` で
引用を閉じたので 19 行でフィールドがずれ、`%6346#%#/&#736%\"#423…` が
「ステータス」として数えられた。distinct な status が 30 → 16 に落ちたのが
その効果である。**壊れた入力ほどずれる。**

**開放アドレス法のキーは、構造を持たせた瞬間に混ぜる。** リンク表のキーは
`(from << 32) | to` で、マスクすると下位ビットが `to` そのものになる。
`status:200` を指すリンクが全部同じスロットに落ち、書き出しが **58.3 秒**に
なった。splitmix64 の finalizer を通して **0.78 秒**。語彙表のキーは FNV の
出力で最初から混ざっていたので、この罠はリンク表を足すまで見えなかった。

**索引を入れても、集計側が二乗なら意味がない。** セグメントを跨いで値を
畳むのに配列を線形に探しており、`ip` (11,293 種) では**索引の方が全走査より
遅かった** (439 ms 対 335 ms)。表引きにして 147 ms。

## 9. 言語側で効いてくる制約

| 制約 | 効き方 |
|---|---|
| 確保したメモリが返らない ([`MEMORY.md`](MEMORY.md)) | 語彙表とリンク表は**セグメント単位で作って捨てる**。語の名前は distinct ごとに 1 つだけ持ち、レコードごとには作らない |
| `Vec::sort` が挿入ソート | 30 万件を並べる場面では使えない。postings とリンクは**計数ソート**で作る (出現順が既に昇順なので比較ゼロ) |
| ~~`Dict<u64, V>` が別モジュールから使えない~~ | `impl Hash for u64` が見えず `expected Hash, got u64` だった。**2026-09-05 に解消** (`Dict` はハッシュ表になり、鍵を splitmix64 で混ぜる)。自前の開放アドレス表は残してある — 探索がそのまま id 割り当てになる形が、置き換えて得るものより大きい |
| gather / scatter が無い ([`SIMD.md`](SIMD.md)) | postings の交差はスカラーのまま。語の切り出しは SIMD が効く |
| スレッドが無い | 索引構築はフラッシュ経路に載る。1 セグメント 8 MiB の予算内 |
