# CONCURRENCY — 並行性に何を入れるか、まだ入れないか

> 状態: **設計は決まった (§5、2026-09-20)。実装は A1 から。**
> todo.md の CONCURRENCY (★★★) と RUNTIME_LIBRARY P3 が「設計文書を
> 別に取ってから着手」と言っている、その文書。2026-09-18 に書き起こし、
> 2026-09-20 に §5 の論点を決めた。

## 0. 要点

- **最初に入れるべきは `spawn` ではない。** ハンドルもチャネルも持たない
  **データ並列** (§4-A) が、今の move / Drop モデルに追加の判定を持ち込まずに
  入る唯一の形である
- **`Send` 相当の判定は、データ並列を 1 回出荷してから決める。** 判定を
  先に決めようとすると、実プログラムが 1 つも無いまま型の話だけが進む
- **4 レーンで答えが割れない形しか採れない。** tree-walker は
  `Rc<RefCell<Object>>` で、本物のスレッドを持てない。仕様が
  「逐次に実行しても同じ答え」を保証しないと、consistency harness も
  `--check` も使えなくなる

## 1. 需要の確認 — サーバは並行性を必要としていない

`poc/logsearch` の HTTP サーバが同時接続 1 本なのは並行性の穴ではない。
**容器から取り出したハンドルの drop glue が fd を閉じる**という別の穴で、
2026-09-18 に 4 レーンで再現を確認した:

```rust
var conns: Vec<TcpStream> = Vec::new()   # 表そのものは作れる
conns.push(cl)
val s: TcpStream = conns.get(0u64)       # 要素の**別名**に drop glue が付く
# `s` の束縛が死ぬと fd が閉じ、表に残った接続は 2 回目の write で
# `unknown error` (EBADF) になる
```

**2026-09-19 / 20 に塞いだ** (ELEMENT-BORROW): 要素を名指す `borrow` が
入り、値で取り出す形は `[E0028]` で拒否される。上の `conns.get(0u64)` は
今はコンパイルエラーで、`conns.borrow(0u64)` と書く。

イベントループ (epoll / kqueue の統一形)、部分読み・部分書き、
タイムアウト、keep-alive はすべて入っている。**同時接続は 2026-09-19 に
128 になり**、2026-09-20 には表が**ハンドルそのもの**を持つ形に戻った
(`Vec<Option<TcpStream>>` — 空きは `None`、使うときは `borrow`、
空けるときは `Vec::replace` で所有を取り戻す)。いずれにせよ
**並行性は要らなかった**。

この取り違えは 1 度実際に起きた (このファイルを書く直前まで、POC の
残タスク一覧は「同時接続は CONCURRENCY 待ち」と書いていた)。並行性の
設計を需要から始めるなら、**サーバは需要ではない**。

残る需要は **CPU 並列**だけで、実測は次のとおり (実ログ 444,549 レコード /
12 セグメント / 25 MB のアーカイブ):

| 仕事 | 今 | 分割の単位 |
|---|---:|---|
| `archive` (読む → 索引を作る → 圧縮して書く) | 1,610〜1,678 ms | 入力ファイル、またはセグメント |
| `query` の全走査 (`status=404`) | 363 ms | セグメント |
| `verify` | 600〜640 ms | セグメント |
| `fields ... scan` | 数百 ms | セグメント |

どれも**セグメント単位で独立**しており、結果は最後に畳むだけである。
これはチャネルもアクターも要らない形の仕事であって、`spawn` + join +
channel の三点セットを最初に入れる理由にはならない。

## 2. 現行モデルから来る制約

### 2-a. 別名が既定である

`val b = a` は compound では**別名**であって move ではない
([`CLAUDE.md`](../CLAUDE.md) の所有権の節)。move 検査 (`[E0014]`) が
働くのは `impl Drop` を持つ型だけで、しかも分岐・ループ本体からの move は
drop flag が無いので拒否される。

つまり「送った値をこちら側はもう触らない」を今の検査で言えるのは
**所有型に限られる**。`Span<T>` / `Column<T>` のような窓は escape 検査が
そもそも無い (POINTER.md の既定)。**共有可変性を静的に止める道具が、今は
無い**と考えてよい。

### 2-b. レーンが 4 つある

| レーン | 実行の実体 | 本物のスレッド |
|---|---|---|
| tree-walker | `Rc<RefCell<Object>>` のグラフ | **不可** (`Rc` は共有できない) |
| IR VM | 単一ヒープ + interpreter プロセス | 不可に近い |
| cranelift JIT | ネイティブコード | 可 |
| AOT | ネイティブコード | 可 |

tree-walker は `--check` と consistency harness の**オラクル**である。
ここで走らない意味論を入れると、その機能はオラクルを失う。したがって:

> **並行の構文は、逐次に実行しても同じ答えを出すものに限る。**

これは制約であると同時に、テスト戦略でもある (`toy test` の
`-j1` と並列で出力がバイト一致する、という既存の流儀と同じ考え方)。

### 2-c. ランタイムの下地は半分ある

- `toylang_rt` の `ThreadState` は **pthread_key TLS で per-thread 化済み**。
  出力シンク (`sink` / `err_sink`) と **allocator スタック**がここに居る
- **shadow stack は 2026-09-21 に per-thread になった** (A2-a)。
  `toy_shadow_ctx()` がスレッドごとの `{ depth, slots }` を返し、
  codegen は prologue で 1 回だけ呼ぶ。実測: 呼び出ししかしない
  マイクロベンチ (6,000 万活性化) が 0.13 → 0.30 秒、`toy test
  poc/logsearch` のような実仕事は +4%。`--release` は frame を
  1 つも記録しないので 0
- ヒープは libc `malloc` なのでスレッド安全。ただし**確保カウンタ**
  (`__builtin_live_bytes` 等) はプロセス全体の数であり、per-thread に
  するか合算にするかは決めていない

### 2-d. allocator と region

`with allocator = arena { ... }` は lexical で、REGION 検査
([`REGIONS.md`](REGIONS.md)) が「スコープ付き allocator から出た値を
外へ出さない」を見ている。**arena を複数スレッドで共有すると、この検査の
前提 (単一の制御フロー) が崩れる。** 最初は「並列ブロックの中は default
allocator 固定」で閉じるのが安全である。

### 2-e. panic はプロセスを終える

言語の規約として例外は無く、`panic` は即時停止である
([`ERROR_MODEL.md`](ERROR_MODEL.md))。スレッドの panic を「join まで
運ぶ」形にすると、その規約に例外機構を持ち込むことになる。**並列ブロックの
中の panic はプロセスを終える**、が現行規約と一貫する。

## 3. 判定 (`Send` 相当) をいつ決めるか

[`EFFECT_SYSTEM.md`](EFFECT_SYSTEM.md) の「この先」は
**「region を跨がない値 = 送れる値」**という定義を挙げている。これは筋が
よいが、**先に決めるべきではない**。理由:

- 判定の良し悪しは「実際に書きたい並列プログラムが通るか」でしか測れない。
  今この言語で書かれた並列プログラムは 1 本も無い
- §4-A の形なら判定そのものが要らない。**要らない形で 1 回出荷し、
  そこで詰まった場所を見てから**判定を設計できる

## 4. 候補 (優先順位つき)

### ★★★ A. データ並列 — ハンドルもチャネルも無い fork-join

```rust
# 形は未決 (§5 の論点 1)。意味の側を先に決める。
par::for_range(0u64, segs.size(), fn (i: u64) -> () {
    # i 番目のセグメントを引く。書き込み先は i で分かれている
})
```

- **`Send` 判定が要らない。** 捕捉できるのはスカラーのコピーと窓
  (`Span<T>` / `Column<T>`) だけで、書き込み先が index で分かれていることは
  呼び出し側の責任 (`requires` で書ける)
- **逐次レーンで同じ答えになる。** tree-walker / IR VM はただのループに
  落とす。AOT / JIT は pthread
- **出力は禁止** (`Io` 効果をマスクする)。並列ブロックの中で `print` を
  許すと出力順が非決定になり、レーン間一致が崩れる。集めた結果を
  ブロックの外で出す形に倒す
- 実需要 (§1 の 4 つ) にそのまま効く

**入るもの**: 構文または stdlib 関数 1 つ、効果マスク 1 行、
`toylang_rt` のスレッド生成 (pthread)、shadow stack の per-thread 化、
consistency テスト (逐次と並列で同じ答え)。

### ★★ D. プロセス並列 — 共有メモリを持たない逃げ道

`io::spawn_process(path, args)` + パイプ。共有メモリが無いので `Send` も
move モデルの拡張も要らず、**全レーンで同じ挙動**になる。粒度は粗いが、
「12 セグメントを 4 プロセスで引く」には足りる。RUNTIME_LIBRARY が
「プロセス spawn は需要未確認」として保留しているものと同じ項目で、
A と排他ではない。

### ★★ B. `spawn` + join ハンドル (A の後)

todo.md が挙げている最小形。`Send` 相当の判定が要る (§3)。加えて
**逐次レーンでの意味が決まらない**のが難所である — spawn 時に即実行すると、
join 前の副作用の順が観測できる形でレーン間の答えが割れる。
A を出荷し、判定の材料が揃ってから。

### ★ C. チャネルとワーカープール (B の上)

デッドロック、ブロッキング、poller との統合が一度に来る。B が無ければ
書けない。

### ★ E. 現状維持 (イベントループのまま)

サーバに関してはこれが正解で、必要なのは §1 の穴 (容器から取り出した
ハンドルが閉じる / `from_fd` が無い) を塞ぐことだけ。
**並行性のタスクではない。**

## 5. 決めたこと (2026-09-20)

§4-A を採る。論点 1〜4 の答えと、その理由。

### 1. 形 — **構文**にする

```rust
parallel for i in 0u64..segs.size() {
    # i 番目のセグメントを引く。書き込み先は i で分かれている
}
```

stdlib 関数 (`par::for_range(from, to, f)`) は**書けない**。AOT の
クロージャが捕捉できるのはスカラーだけで (CLOSURE_CAPTURE)、§1 の
仕事はどれも窓か容器を要る — セグメントの一覧、出力の列。捕捉を
拡張してから関数形を入れるより、**本文をその場に置く**ほうが小さい:
本文は囲みの束縛をそのまま名指せて、それは今の `for` と同じである。

副産物が 2 つある。**逐次レーンはただの `for`** なので、意味論を
先に出荷して並列化を後から足せる (下の段取り)。そして**効果の
マスクを掛ける場所が構文の 1 点に決まる** — 関数形なら「渡された
クロージャ」を追う必要があった。

### 2. 並列度 — コア数、`TOY_PAR_THREADS` で上書き

`toy test` と同じ既定。**意味論ではない**ので言語仕様には書かない:
並列度は答えを変えてはならず、変えるなら本文が間違っている。

### 3. disjoint — **規約で守る**

型で守るには `Span::split_at` のような分割 API と、この構文のためだけの
別名規則が要る。窓は今も escape しか見ておらず (POINTER.md の既定)、
**規則を 2 つに分けない**。書き込み先が添字で分かれていることは
呼び出し側の責任で、`requires` に書ける。破れば競合するが、それは
`Span` を 2 本重ねたときと同じ性質の間違いである。

### 4. 逐次レーンの意味 — **完全逐次** (添字の昇順)

ラウンドロビンにすると「逐次でも同じ答え」の保証が弱くなる。
tree-walker と IR VM は `for` と 1 バイトも変わらない実行をする。
並列レーンは**順序を保証しない** — 本文が添字で分かれている限り
答えは同じで、分かれていなければどちらの順でも間違っている。

### 5. 確保カウンタ — 合算

per-thread にすると `--profile=mem` の数がスレッド数で割れて、
「このプログラムが何バイト持っているか」を答えなくなる。
**並列ブロックの中で `ensures allocates(N)` を書かない**ことを規約に
する (書けてしまうが、意味は「全スレッドの合計」になる)。

### 本文に許さないもの

- **出力** (`Io`) — 並べ替わった出力はレーン間一致を壊す。集めて
  ブロックの外で出す。`never_allocates` / `const fn` と同じ到達可能性
  検査で断る
- **`with allocator = ...`** — REGION 検査は単一の制御フローを前提に
  している (§2-d)。並列ブロックの中は default allocator 固定
- **panic はプロセスを終える** (§2-e)。join まで運ばない

## 6. 段取り

| | 中身 | 単独で出荷できるか |
|---|---|---|
| **A1** | 構文 + 検査 (Io / allocator) + **4 レーンとも逐次**で実行 | **可**。意味論と診断がここで固まり、以後の並列化は答えを変えられない |
| **A2-a** | shadow stack の per-thread 化 | **2026-09-21 に landing**。`toy_shadow_stack` / `toy_shadow_depth` の 2 つのグローバルが `toy_shadow_ctx()` が返す**スレッドごとの記録**になった (`{ depth, slots }`、既存の pthread_key TLS の上)。codegen は prologue で 1 回呼ぶだけ — 番地は活性化の間は定数のままなので、hoisting の前提は変わらない |
| **A2-b-1** | `toylang_rt` の `toy_par_for` (pthread と範囲分割) | **2026-09-21 に landing**。`toy_par_for(from, until, env, body)` が範囲を割ってスレッドに配り、**呼び出し元も 1 区間を担当する** (1 スレッドなら spawn 0)。スレッド数は `TOY_PAR_THREADS`、既定は `sysconf(_SC_NPROCESSORS_ONLN)`、上限 64。ジョブは呼び出し元のフレームに置くので**確保ゼロ** (プロファイラに見えない)。テストは「どう割っても各添字がちょうど 1 回」と「8 スレッドは 1 スレッドより速い」 |
| **A2-b-2** | lowering が本文を切り出し、`toy_par_for` を呼ぶ | **2026-09-21 に landing**。`compiler_lower/src/parallel.rs`。捕捉は呼び出し元フレームのスロットに置き (`dyn_coerce_slots`、**確保ゼロ**)、`InstKind::ParFor` が AOT / JIT では `toy_par_for`、IR VM では「1 区間として本文を 1 回呼ぶ」になる。逐次との一致は `compiler/tests/consistency/parallel_for.rs` が縛る |

### A2-b をどこで切り出すか — **lowering** (2026-09-21 に訂正)

最初ここには「フロントエンドの desugar で」と書いていた。**できない**:
フロントエンドは**宣言を新造できない**。env struct と本文関数を
型検査の途中で足すことになるが、この層の書き換えは `?` / `??` /
`Display` のような**式の差し替え**しか持っていない。

`compiler_lower` は逆に、**関数を新造するのが日常**である —
generic の単相化 (`instantiate_generic_function`) も drop glue も
`declare_function_anon` で関数を宣言し、body を後で埋める作業待ち
行列に積む。並列本文はまさにその形をしている:

- `declare_function_anon("__par_body_N", Local, [env: ptr, from: u64, until: u64], Unit)`
- 捕捉したものは呼び出し側フレームの**スタックスロット**に置き、
  その番地を渡す (ポインタ渡し ABI の `receiver_address` と同じ手口)
- 逐次レーン (tree-walker / IR VM) は**本文をその場で回す**ので、
  切り出し自体が要らない

型の情報が要る作業 (どの捕捉が窓でどれがスカラーか) も、IR には
型があるので lowering のほうが素直である。

```rust
parallel for i in a..b { out.set(i, work(i)) }
```

が、およそ次に化ける:

```rust
struct __ParEnv0 { out: Span<u64>, base: u64 }   # 捕捉したもの
fn __par_body0(env: &__ParEnv0, from: u64, until: u64) {
    var i = from
    while i < until { env.out.set(i, env.base + work(i))  i = i + 1u64 }
}
# ランタイムが範囲を割って、スレッドごとに本文を呼ぶ
__builtin_par_for(__par_body0, &env, a, b)
```

**クロージャにはできない。** AOT のクロージャが捕捉できるのは
スカラーだけで (CLOSURE_CAPTURE)、並列にしたい仕事はどれも容器か窓を
要る。env を明示の struct にするのはそのためで、ついでに「何を
捕捉したか」が診断に出せる。

### env が持てるのは**スカラーと窓**だけ (2026-09-21 に確かめた)

最初この節は `out: &mut Vec<u64>` と書いていた。**書けない** —
`struct S { r: &u64 }` は REF-Stage-2 (e) が拒否する
(`references cannot be stored in struct fields`)。参照を持てる env は
今の言語には無い。

代わりに**窓**を持つ。`Span<T>` / `Column<T>` はただの struct なので
フィールドに置けて、`set` で元のバッファに書ける — 添字で分かれた
書き込みという §1 の仕事に必要なのは、まさにそれである。上の形は
**3 レーンで動くことを確認した** (`Env { out: Span<u64>, base: u64 }`
を `work(&e, from, until)` が 2 回に分けて埋め、答えは逐次と同じ)。

これは制限であると同時に、§5-3 の「disjoint は規約で守る」を書きやすく
する: 捕捉できるものが窓とスカラーだけなら、**書き込み先は窓の添字
しかない**。窓にできない捕捉 (`String`、`Dict`、値で使う `Vec`) は
診断で断り、「窓を渡せ」と言う。

残る論点は 3 つ、どれも実装中に決まる類のもの: 捕捉した**スカラーへの
書き込み**をどう断るか (競合なので断る)、**入れ子の `parallel for`**
(外側だけ並列でよい)、`self` を捕捉したときの綴り。

A1 を先に出すのは、**並列化が最適化になる**ようにするためである。
「逐次と並列で答えが同じ」を後から確かめるのではなく、逐次の答えを
先に固定してから並列を足す。**実際そうなった** — A2-b-2 で
consistency のテストは 1 つも変わっていない (アキュムレータを使って
いた 2 本を除く。下記)。

### 実装で決まった 3 点 (2026-09-21)

**1. env は呼び出し元フレームのスロット。** 当初は closure の
`MakeClosure` を流用して書いたが、あれは `malloc` する — ホットな
経路に置いた `parallel for` が実行ごとに env を漏らすことになるし、
「ジョブは呼び出し元のフレームに置くから確保ゼロ」という A2-b-1 の
約束を、その上の層が破る。`&dyn Trait` の coercion が使っている
`dyn_coerce_slots` (フレームのバイトスロット) がそのまま使えたので、
**新しい命令を足さずに**スタックに移した。副産物として IR VM の
`dyn_coerce_addr` が `alloc_internal` を使うようになり (フレーム
スロットは確保ではない)、**`&dyn Trait` の coercion で確保カウンタが
レーン間で割れていた既存の食い違いも消えた**。

**2. 渡すのは添字ではなく「個数」。** `ParFor` は常に `0..count` を
受け、本文が base を足し直す。こうすると `parallel for i in
-3i64..3i64` が特別扱い無しで通る — 符号付きの端点を unsigned で
割ろうとすると `end - start` が破綻する。空・逆順の範囲は count が
0 になる (逐次の header が最初の比較で出すのと同じ答え)。

**3. 捕捉への書き込みは断る。** env に入るのは**写し**なので、
本文がそれに書けば呼び出し元には届かず、届いていたら競合している。
検査は**ソースではなく生成後の IR**に対して行う (`x = ..` /
`s.field = ..` / `&mut self` の writeback を 1 つの規則で捕まえる)。
しかも **writeback の枝刈り (CODE-SIZE-WB-PRUNE) の後**に走らせる —
`v.set(i, x)` は ABI 上 `v` の全 leaf を返すが 1 つも書かないので、
枝刈り前に訊くと「ベクタに書いた」ように見える。**並列本文でいちばん
普通の行が、それで断られるところだった。**

窓越しの書き込みは捕捉への書き込みではない (`set` は写しが持つ番地に
store する。写しは無傷)。

### モジュールの中では `parallel for` ではなかった (2026-09-21)

A1 が「どのレーンも逐次で回す」を固めた対象は、**パーサが
`File::parallel_loops` に記録した `for`** である。その表を統合が
写していなかったので、**モジュールの中に書いた `parallel for` は
ただの `for`** だった — 本文が `println` でき (E0029 が走らない)、
lowering も切り出さない。逐次の答えを先に固定したはずの構文が、
その構文ではなかったことになる。統合が写すようになった
(`call_paths` と `const` も同じ一家)。

### E0029 が増えた 2 つ

`break` / `return` と、**外側の名前への代入**。どちらも
「順序が観測できる」側であって lowering の都合ではないので、
型検査器で断る — でないと tree-walker だけがアキュムレータを
平然と回す。A1 のテストのうち 2 本がアキュムレータで書かれていたので、
添字ごとのスロットに書き直した (答えは同じ)。

**残っている非対称**: 外側の束縛を**変える method 呼び出し**
(`v.push(x)`) は lowering が断り、tree-walker は通す。`push` が
`v` に書くことは callee のシグネチャを読まないと分からないので、
型検査器側に同じ検査を置くと**近似の二重実装**になる。今は
「インタプリタで動いた形が AOT で落ちる」形の 1 つとして残す。
