# STORAGE_FORMAT — ディスク上の形式 (v3)

すべて**リトルエンディアン**。整数は幅を明記する (`u32` / `u64`)。
可変長整数は LEB128 を `varint` と書く。オフセットは特記しない限り
そのファイルの先頭からのバイト数。

## 0. v2 から何が変わったか (2026-09-05)

**セグメントは 1 ファイルに戻った。** v2 がデータ `.dat` と索引 `.idx` を
分けていたのは性能の設計ではなく**可能性の設計**で、「読めるのはファイル
全体だけ」という制約への応答だった。同じ理由でセグメントは 8 MiB に
抑えてあった (丸ごと読んでも許される大きさ)。

`core/std/fs.t` に `File` が入り (`read_at` / `write_at` / `sync` /
`truncate`)、**その 2 つの根拠が同時に消えた**。

| v2 の判断 | 根拠 | v3 |
|---|---|---|
| `.idx` を別ファイルにする | 索引だけ読めない | **1 ファイル `.seg`** に統合。セクション表が中の位置を持つ |
| セグメントは 8 MiB 上限 | 丸ごと読むしかない | **上限ではなく選択**。フレーム単位で読むので、大きくしてよい |
| 公開は rename 2 回 (順序が要る) | 2 ファイルある | **rename 1 回**。「本体はあるが索引が無い」瞬間が消えた |
| 耐久性は OS 任せ | `fsync` が無い | **`File::sync()`** を公開の前に呼ぶ |
| ヘッダを読むのにファイルを読む | 部分読みが無い | **320 バイトだけ読む** |

実測 (実ログ 30.5 MB / 181,519 行、AOT `--release`):

| | v2 (2 ファイル・全体読み) | v3 (1 ファイル・`read_at`) |
|---|---|---|
| アーカイブ作成 | 826 ms | **785 ms** |
| 検証 (`verify`) | 273 ms | **251 ms** |
| `status=404` (全走査) | 425 ms | **370 ms** |
| 部分一致 (全走査) | 228 ms | **183 ms** |
| `top=status` (索引のみ) | 34 ms | **24 ms** |
| traversal (リンクのみ) | 48 ms | **35 ms** |
| 時刻で全部枝刈り | 33 MB 読む | **1,280 バイト / 0 ms** |
| クエリの peak live | 64 MiB のバッファを先に確保 | **22.7 MB** (実測) |

最後の 2 行がこの変更の本体である。**「読まない」が本当に読まなくなった** —
v2 の枝刈りはヘッダを見るために `.dat` を全部読んでいたので、
枝刈りされた側も走査とほぼ同じ I/O を払っていた。

> **既存データは読めなくなる。** マジックは `LSD2` → `LSD3`、
> `.dat` / `.idx` は `.seg` になった。POC の段階なので互換は取らない
> (アーカイブはログから 0.8 秒で作り直せる)。**形式を凍結すると
> 宣言したあとはこのやり方をしない** — [`ROADMAP.md`](ROADMAP.md) の
> 「形式のバージョニング」に従い、上げたバージョンで**両方読める**
> ようにする。

### セグメントの大きさを測った

8 MiB を保つ理由はもう無いので、32 MiB で測った:

| | 8 MiB | 32 MiB |
|---|---|---|
| セグメント数 | 4 | 1 |
| 保存サイズ | 9.12 MB | **8.82 MB** (-3%) |
| 作成 | 785 ms | 773 ms |
| `top=status` | 24 ms | 20 ms |

**大きい方が縮む** (圧縮の窓が長い、ヘッダとセクションの固定費が減る)。
それでも既定を 8 MiB のままにしてあるのは、**時刻の枝刈りとリンク索引が
セグメント単位**だからで、1 本にまとめるとその粒度が消えるため。
運用では「保持期限の削除単位」でもあるので、**日あたりのログ量から
逆算するのが正しい**。

## 0b. 形を決めている制約 (残っているもの)

普通のログストアと違う判断をしている箇所は、ほぼすべてここから来ている。

1. **確保したメモリが返らない** — この処理系の割り当ては解放しても
   再利用されない ([`MEMORY.md`](MEMORY.md))。だから読み手のバッファは
   **走査全体で 1 組**を使い回す。セグメントごとに確保する形は、
   v2 の `expand` が実際にそうなっていて、コーパスに比例して
   常駐が伸びていた
2. **`Vec::sort` が挿入ソート** — 数十万件を並べる場面では使えない。
   postings とリンクは**計数ソート**で作る (出現順が既に昇順なので比較ゼロ)
3. **標準の圧縮形式が無い** — 自前の LZ77 (`LSZ1`, §5)。`zcat` できない
   代償を承知で使っている ([`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) G7)

> ファイルの列挙・作成・削除・改名は 2026-09-03 に `core/std/fs.t` で、
> 部分読み書きと `fsync` は 2026-09-05 に `fs::File` で入った。
> v1 の設計 (マニフェスト唯一真実 / tombstone / 世代 / フラット配置) と
> v2 の 2 ファイル構成は**すべてその不在への応答**だったので、
> この文書は書き直してある。経緯は git log にある。

> **実装状況** (2026-09-05): `src/segfile.t` がファイル層 (ヘッダ・
> セクション表・`read_at` / `write_at` / フレーム展開)、`src/archive.t`
> が書き手とセクションの意味を持つ。`archive::verify` が読み戻して
> 全フレームの CRC・レコード表の件数・圧縮セクションの展開可否を
> 照合する。**まだ無いのは §6〜§8** (カタログ / マウント / 保持期限)。
> 時刻は**秒**で格納している (パーサが秒しか読まないため)。

## 1. マウントのディレクトリ構成

```
<mount>/
  meta/
    mount.json                     # マウントの素性 (JSON、起動時に 1 回書く)
    catalog.000007.snap            # カタログのスナップショット (rename で公開)
    catalog.000007.log             # 以降の変化 (追記のみ)
  seg/
    2026/09/03/
      000000000042.seg             # セグメント (本体 + 索引)
      000000000117.arc.seg         # アーカイブ (併合結果)
  tmp/
    000000000043.seg.part          # 書きかけ。公開は rename
```

- **日付で切る** (`seg/YYYY/MM/DD/`) のは、保持期限の削除が
  `list_dir` 1 回 + `remove_file` の並び + `remove_dir` で閉じるから。
  日付はセグメントの `ts_min` を UTC で見たもの
- **`tmp/` は同じマウントの中に置く。** `rename` が原子的なのは同一
  ファイルシステム内だけなので、`/tmp` を使ってはいけない
- パスの組み立ては `path::join` を使う。手で `+ "/" +` すると
  末尾スラッシュの有無で壊れる
- ディレクトリは `fs::mkdir_all` で必要になった時点で作る

### `meta/mount.json`

JSON リーダが入った (`core/std/json.t`) ので、素性は人間が読める形にする。

```json
{
  "format": 3,
  "uuid": "0f3c...",
  "created_unix_ns": 1756900000123456789,
  "created_by": "logsearchd 0.1",
  "note": "disk2"
}
```

起動時にこれが無ければ書く。あって UUID が設定と食い違えば
**degraded にして触らない** — 別のマウントのディレクトリを取り違えて
上書きするのが、この設計で最も高くつく事故だからである。

## 2. セグメントの公開 — tmp に書いて rename

```
1. tmp/000000000042.seg.part を開く      (File::create)
2. 320 バイトの予約を書く                 ← ヘッダとセクション表の場所
3. フレームを 1 つずつ書く                (File::write)
4. レコード表・フレーム表・語彙・リンクを書く
5. ヘッダとセクション表を書き戻す         (File::write_at(0, ...))
6. sync する                             (File::sync) ← ここまでで耐久
7. seg/2026/09/03/ を用意する            (mkdir_all)
8. rename して置く                       ← これが公開の瞬間
9. カタログのジャーナルに 1 行追記する    (append_file_bytes)
```

**rename は 1 回**。v2 は `.dat` と `.idx` を順に置いていたので
「本体はあるが索引が無い」瞬間があり、順序を規約で縛っていた。
1 ファイルになった今、その状態は**表現できない**。

**5 が最後なのは、書き終わるまで長さもオフセットも分からないから**である。
ファイルは 320 バイトの穴で始まり、全部書けたところで
`write_at(0, ...)` が埋める。**途中で落ちたファイルはマジックが 0 のまま**
なので、読み手は「セグメントではない」と判断して飛ばす —
中途半端に読めてしまう状態が無い。

**6 の `sync` が耐久の線**である。これが返るまでバイトはディスクに
無い。v2 には `fsync` が無く「プロセスの死には強い、ホストの電源断には
強くない」と書いてあった (§9)。今は電源断にも耐える。

9 が失敗しても、あるいは 8 の直後に落ちても、**次の起動が
`list_dir` で見つけて拾う**。カタログは真実ではないので、遅れて追いつけばよい。

途中で落ちて残った `tmp/*.part` は、起動時に `list_dir(tmp)` して消す。

## 3. セグメントファイル `.seg`

```
┌────────────────────┐
│ header (64B)       │  ← カタログの 1 行そのもの
│ section directory  │  ← count + 8 スロット × (kind, off, len, crc)
├────────────────────┤ 320
│ frames             │  ← 圧縮された本文アリーナ (kind 1)
├────────────────────┤
│ record table       │  ← レコードの列 (kind 2)
│ frame table        │  ← フレームの位置と担当範囲 (kind 3)
│ term dictionary    │  ← 語彙索引 (kind 6、圧縮)
│ link table         │  ← 共起リンク (kind 7、圧縮)
│ object table       │  ← 語ごとの first/last (kind 8、圧縮)
└────────────────────┘
```

**読み手は必要な部分だけ取る。** 枝刈りは 320 バイト、`top=` のような
集計は語彙セクション 1 本、本文の走査は**索引が残したレコードが載って
いるフレームだけ**。

### ヘッダ (64 バイト)

| off | 型 | 意味 |
|---|---|---|
| 0 | u8[4] | `"LSD3"` |
| 4 | u32 | 形式バージョン (= 3) |
| 8 | u64 | `segid` |
| 16 | u64 | `ts_min` (実装は**UNIX 秒**、§0b) |
| 24 | u64 | `ts_max` |
| 32 | u64 | レコード数 |
| 40 | u32 | フレーム数 |
| 44 | u32 | フレームあたりの非圧縮サイズ (既定 262144) |
| 48 | u64 | 本文アリーナの非圧縮総バイト数 |
| 56 | u32 | 種別 (0 = segment, 1 = archive) |
| 60 | u32 | ヘッダ CRC-32 (0..60 に対して) |

**ヘッダだけでカタログの 1 行が作れる**ように全部入っている。
`--repair` (§7) は「ディレクトリを歩いて先頭 320 バイトを読むだけ」で、
v2 のように**ファイル全体を読む必要はもう無い**。

### セクション表 (offset 64、256 バイト)

| off | 型 | 意味 |
|---|---|---|
| 64 | u32 | セクション数 (現在 5) |
| 68 | u32 | 予約 (0) |
| 72 | … | 8 スロット × 24 バイト: `u32 kind` / `u64 off` / `u64 len` / `u32 crc` |

`kind` は 1 = frames / 2 = records / 3 = frame table / 6 = terms /
7 = links。**知らない kind は飛ばす**ので、セクションを足しても
古い読み手は壊れない。スロットを 8 本の固定長にしてあるのは、
ヘッダごと 1 回の `read_at` で取れる大きさに収めるため。

セクションの中身は 320 バイト目から始まる。

### フレーム

| off | 型 | 意味 |
|---|---|---|
| 0 | u8[4] | `"LSF1"` |
| 4 | u32 | コーデック (0=stored, 1=LSZ1) |
| 8 | u32 | 非圧縮バイト数 |
| 12 | u32 | 圧縮後バイト数 |
| 16 | u32 | 非圧縮データの CRC-32 |
| 20 | u32 | 予約 (0) |
| 24 | … | ペイロード |

**フレームは自己完結する** (LZ77 の窓はフレームを跨がない)。前のフレームを
読まずに展開できる。v3 では**読み取りもフレーム単位**になったので、
走査中にメモリに載るのは 1 フレーム (256 KiB) + 展開先のアリーナだけ
になった。フレーム表 (kind 3) が各フレームの
`(ファイル内オフセット, アリーナ内オフセット, 非圧縮長)` を持つので、
**要るフレームだけ読む**こともできる (未実装。候補レコードが
どのフレームに載るかは表から引ける)。

## 4. 索引のセクション

v2 では別ファイル `.idx` だった。統合しても**中身は変わっていない** —
セクション表がファイルの中の位置を指すようになっただけである。

```
kind 2  record table   レコードの列 (SoA varints、非圧縮)
kind 3  frame table    フレームのオフセットと担当範囲 (20 バイト固定長)
        ↑ 索引で絞ったクエリが「どのフレームを展開するか」を決めるのに
          使う。飛ばしたフレームは**展開せず長さだけ進める**ので、
          アリーナのオフセットはレコード表が言うとおりに保たれる
kind 6  term dictionary 語彙索引 (転置、LSZ1 圧縮)
kind 7  link table     共起リンク (LSZ1 圧縮)
kind 8  object table   語ごとの first_seen / last_seen (LSZ1 圧縮)
```

kind 8 は語の id 順に `has: varint` と、`has` なら `first: varint` +
`last - first: varint` を並べる。件数は kind 6 が持っているので重複
させない。**日付の無い行にしか現れなかった語は `has = 0`** —
「不明」を番兵の時刻で表さないための 1 バイトである
([`ONTOLOGY.md`](ONTOLOGY.md) §5-b)。

圧縮したセクション (6 / 7 / 8) は自分のフレームヘッダを持つ:
`"LST1"`, codec, 非圧縮長, 格納長, 非圧縮 CRC-32。読み手は
`read_at` でその範囲だけ取り、展開して CRC を照合する。

### 2. record table (SoA)

```
ts_base: u64                       # = ts_min (UNIX ns)
ts_delta:   varint[N]              # ts - 直前の ts (ストリーム内で単調増加)
seq_delta:  varint[N]
stream_id:  varint[N]
body_off:   varint[N]
body_len:   varint[N]
flags:      varint[N]
```

**列ごとに置く (SoA)** のは、クエリが列を 1 本だけ舐める場面が多いから。
時刻範囲の判定は `ts` 列しか要らない。加えて、この形は将来の
**自動ベクトル化の入口**でもある ([`SIMD.md`](SIMD.md) §7)。

ns にしても、隣接レコードの差分は小さい (1 秒に 5,000 行なら平均 200µs =
varint 3 バイト) ので、サイズはほとんど変わらない。

### 6. 語彙索引 (bloom は未実装)

語は**初出順**に置いて読み手が 1 パスでハッシュ表を作る (設計は辞書順 +
二分探索だが、2 万語を `Vec::sort` で並べると挿入ソートで二次になる)。
転置リストは delta-varint。

bloom フィルタ (8 KiB) は設計だけで、まだ書いていない。**部分読みが
入った今、置き場所は「セクション表の直後」で正しい** — ヘッダと同じ
1 回の `read_at` に載る位置だからである。

## 5. 圧縮コーデック `LSZ1`

標準形式 (gzip / zstd) は今も無い ([`RUNTIME_GAPS.md`](RUNTIME_GAPS.md) G7)
ので、自前の LZ77 を持つ。窓 64 KiB、最小マッチ 4、ハッシュ表 32768 の
greedy マッチ、トークンは LZ4 のブロック形式に似た形。**出力が入力の 7/8 を
超えたら `stored`** で書く。

マッチ延長 (16 バイトずつの一致判定) とリテラルのコピーは `u8x16` で
ベクトル化してある (2026-09-04、圧縮 1.4x / 展開 3.0x、出力は
スカラー版とバイト単位で一致)。**展開側の重なりマッチ (offset < 16) は
16 バイトコピーにしない** — 同じ呼び出しがまだ書いていないバイトを
読むことになるため、そこだけは 1 バイトずつが定義そのものである。
詳細は [`SIMD.md`](SIMD.md) §3 P5 / §5 / §6。

CRC-32 は**ベクトル化できない** (carry-less multiply が無い) のでスカラーの
テーブル方式。表は起動時に `Vec<u32>` へ作る。

ラウンドトリップは `--check` のプロパティテストと `--all-backends` の
両方で縛る。ここが割れると、書いたログが二度と読めなくなる。

## 6. カタログ — スナップショット + ジャーナル

カタログは**キャッシュ**である。無ければ作り直せる (§7)。あるのは
「10 万セグメントのマウントを 100ms で開く」ためだけ。

### スナップショット `meta/catalog.<gen>.snap`

その時点の生きたセグメント全部を、1 行 64 バイトの固定長で並べたもの。

| off | 型 | 意味 |
|---|---|---|
| 0 | u64 | `segid` |
| 8 | u64 | `ts_min` |
| 16 | u64 | `ts_max` |
| 24 | u64 | レコード数 |
| 32 | u64 | `.seg` のバイト数 |
| 40 | u32 | 索引セクションの合計バイト数 |
| 44 | u32 | 種別 (segment / archive) |
| 48 | u32 | ストリーム数 |
| 52 | u32 | 語数 |
| 56 | u32 | 日付キー (`YYYYMMDD`、パスを組むのに使う) |
| 60 | u32 | 行 CRC-32 |

先頭に 32 バイトのヘッダ (マジック `"LSC2"`、gen、行数、全体 CRC)。
**固定長にしたのは、`file_size` で行数を検算できるから**である。

### ジャーナル `meta/catalog.<gen>.log`

スナップショット以降の変化を追記する。1 レコードは
`{マジック, 全長, 種別, CRC, 本体}` で、種別は `ADD` (スナップショットの
1 行と同じ内容) と `REMOVE` (`segid` + 理由) の 2 つだけ。

### 世代の交代 (コンパクション)

ジャーナルが 4 MiB を超えるか、起動のたびに:

```
1. tmp/catalog.<gen+1>.snap.part を書く        (現在のカタログ全体)
2. meta/catalog.<gen+1>.snap へ rename          ← ここで新世代が有効になる
3. meta/catalog.<gen>.snap を remove_file
4. meta/catalog.<gen>.log を remove_file
```

**2 の rename が切り替えの瞬間**で、それより前に落ちれば旧世代が、
後に落ちれば新世代が読まれる。どちらも一貫している。3/4 に失敗して
古い世代が残っても、起動は `list_dir(meta)` で**最大の gen** を選ぶので
無害 (次の起動が掃除する)。

v1 の「破損したら世代を上げて書き直す」という仕掛けは**消えた**。
切り詰めができない世界での苦肉の策だったが、rename があれば
コンパクションが同じ仕事を素直にやる。

### ジャーナルの末尾が壊れていたら

CRC が合う最後のレコードまでを採用し、そこで止める。**そして
その場でコンパクションする** (新世代を書いて古いのを消す)。
壊れた末尾は次の瞬間には消えている。

## 7. 起動と再構築

### 通常の起動

```
1. meta/mount.json を読み、UUID を照合
2. list_dir(meta) で最大 gen のスナップショットを見つける
3. スナップショットを読む (10 万行で 6.4 MB、1 回の read)
4. 同じ gen のジャーナルを再生する
5. list_dir(tmp) の残骸を消す
6. 直近 N 個 (既定 64) のセグメントだけ fs::file_size で検算する
```

6 を**直近だけ**にするのは、10 万回の `file_size` を起動のたびに払う
価値が無いから。古いセグメントの欠落は、クエリが触った瞬間に
`NotFound` で気づいて `REMOVE` をジャーナルへ書く (遅延して気づき、
気づいた事実が残る)。

### `--repair` — カタログを捨てて作り直す

```
1. list_dir(seg/YYYY/MM/DD) を全部歩く
2. .seg ごとに先頭 320 バイトを読み、CRC を確かめて 1 行を作る
3. マジックが合わない / ヘッダ CRC が合わないものは quarantine へ rename
4. 新しいスナップショットを書いて公開する
```

**320 バイトで済む**のが v3 の効きどころで、v2 はここでファイルを
丸ごと読んでいた。**これができること自体が v2 の要点である。** v1 ではマニフェストが
壊れた時点で、そのマウントのデータは「存在しないもの」になっていた。

## 8. 保持と削除

保持期限 (既定 14 日) を過ぎたセグメントは、**実際に消す**。

```
1. カタログから外す (ジャーナルに REMOVE)
2. grace period (既定 60 秒) 待つ            ← 実行中のクエリが掴んでいる
3. remove_file(.seg)
4. その日のディレクトリが空になったら remove_dir
```

**grace period が要るのは、参照カウントを持たないから。** クエリは
開始時に触るセグメントの `segid` 集合を持つので、厳密にやるなら
「実行中のどのクエリにも含まれない」を条件にできる。実装は
まずクエリ集合を見て、それが空でなければ 60 秒の期限も併用する
(単調時計 `time::now_mono_ns` が使えるようになったので、これが書ける)。

アーカイブへの併合も同じ形になった: 併合後に元セグメントを消す。
v1 の「tombstone にして `/v1/admin/reclaimable` を外部の `rm` に渡す」は
**廃止**する ([`HTTP_API.md`](HTTP_API.md) から該当エンドポイントを外す)。

## 9. 残る制約

### 耐久性 — `File::sync()` を呼んでいる

`rename` は**順序**の原子性を与える。耐久性は `sync` が与える。
公開の rename より前に `File::sync()` を呼ぶので (§2 の 6)、

> **プロセスの死にもホストの電源断にも、公開済みのセグメントは残る。**

v2 まではここに「電源断には強くない」と書いてあった。`fsync` が
無かったからで、2026-09-05 に `fs::File` が入って解消した。
カタログのジャーナル追記はまだ `append_file_bytes` (sync 無し) なので、
**落ちた直後にジャーナルの末尾が欠けることはある** — カタログは
キャッシュなので、`--repair` が作り直せる範囲に収まっている。

### 部分読み — 入った

`.idx` を別ファイルにしていた理由、セグメントを 8 MiB に抑えていた理由、
`--repair` がファイル全体を読んでいた理由は、すべて `seek` / `pread` が
無いことだった。2026-09-05 に `fs::File` で入り、**この文書の §0 から §4
までがそれに合わせて書き直された**。残っているのは:

- **入力側はまだ全体読み** — ログファイルは `io::read_file_into` で
  1 回に読む (16 MiB 上限)。行がチャンク境界を跨ぐ扱いが要るだけで、
  `File::read` で流せる
- **フレーム単位の選択読みは未実装** — フレーム表は書いてあるので、
  候補レコードの載るフレームだけ展開する形にできる

### 空き容量 — `statfs` が無い

マウントの容量管理は宣言値 (`quota`) のまま。`fs::file_size` で
**自分が書いた分の実測**はできるようになったので、`du` 相当は自前で
持てる (カタログの合計がそれ)。他のプロセスの消費は依然として見えない。
