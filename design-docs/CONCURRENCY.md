# CONCURRENCY — 並行性に何を入れるか、まだ入れないか

> 状態: **設計は決まった (§5、2026-09-20)。実装は A1 から。**
> todo.md の CONCURRENCY (★★★) と RUNTIME_LIBRARY P3 が「設計文書を
> 別に取ってから着手」と言っている、その文書。2026-09-18 に書き起こし、
> 2026-09-20 に §5 の論点を決めた。

## 0. 要点

- **最初に入れるべきは `spawn` ではない。** ハンドルもチャネルも持たない
  **データ並列** (§4-A) が、今の move / Drop モデルに追加の判定を持ち込まずに
  入る唯一の形である
- **`Send` 相当の判定は、データ並列を 1 回出荷してから決める。** 判定を
  先に決めようとすると、実プログラムが 1 つも無いまま型の話だけが進む
- **4 レーンで答えが割れない形しか採れない。** tree-walker は
  `Rc<RefCell<Object>>` で、本物のスレッドを持てない。仕様が
  「逐次に実行しても同じ答え」を保証しないと、consistency harness も
  `--check` も使えなくなる

## 1. 需要の確認 — サーバは並行性を必要としていない

`poc/logsearch` の HTTP サーバが同時接続 1 本なのは並行性の穴ではない。
**容器から取り出したハンドルの drop glue が fd を閉じる**という別の穴で、
2026-09-18 に 4 レーンで再現を確認した:

```rust
var conns: Vec<TcpStream> = Vec::new()   # 表そのものは作れる
conns.push(cl)
val s: TcpStream = conns.get(0u64)       # 要素の**別名**に drop glue が付く
# `s` の束縛が死ぬと fd が閉じ、表に残った接続は 2 回目の write で
# `unknown error` (EBADF) になる
```

**2026-09-19 / 20 に塞いだ** (ELEMENT-BORROW): 要素を名指す `borrow` が
入り、値で取り出す形は `[E0028]` で拒否される。上の `conns.get(0u64)` は
今はコンパイルエラーで、`conns.borrow(0u64)` と書く。

イベントループ (epoll / kqueue の統一形)、部分読み・部分書き、
タイムアウト、keep-alive はすべて入っている。**同時接続は 2026-09-19 に
128 になった** (サーバ本体は番号の表のまま — poller の token に対応する
固定スロットが要り、`Vec<TcpStream>` には「空き」を書けないため)。
いずれにせよ**並行性は要らなかった**。

この取り違えは 1 度実際に起きた (このファイルを書く直前まで、POC の
残タスク一覧は「同時接続は CONCURRENCY 待ち」と書いていた)。並行性の
設計を需要から始めるなら、**サーバは需要ではない**。

残る需要は **CPU 並列**だけで、実測は次のとおり (実ログ 444,549 レコード /
12 セグメント / 25 MB のアーカイブ):

| 仕事 | 今 | 分割の単位 |
|---|---:|---|
| `archive` (読む → 索引を作る → 圧縮して書く) | 1,610〜1,678 ms | 入力ファイル、またはセグメント |
| `query` の全走査 (`status=404`) | 363 ms | セグメント |
| `verify` | 600〜640 ms | セグメント |
| `fields ... scan` | 数百 ms | セグメント |

どれも**セグメント単位で独立**しており、結果は最後に畳むだけである。
これはチャネルもアクターも要らない形の仕事であって、`spawn` + join +
channel の三点セットを最初に入れる理由にはならない。

## 2. 現行モデルから来る制約

### 2-a. 別名が既定である

`val b = a` は compound では**別名**であって move ではない
([`CLAUDE.md`](../CLAUDE.md) の所有権の節)。move 検査 (`[E0014]`) が
働くのは `impl Drop` を持つ型だけで、しかも分岐・ループ本体からの move は
drop flag が無いので拒否される。

つまり「送った値をこちら側はもう触らない」を今の検査で言えるのは
**所有型に限られる**。`Span<T>` / `Column<T>` のような窓は escape 検査が
そもそも無い (POINTER.md の既定)。**共有可変性を静的に止める道具が、今は
無い**と考えてよい。

### 2-b. レーンが 4 つある

| レーン | 実行の実体 | 本物のスレッド |
|---|---|---|
| tree-walker | `Rc<RefCell<Object>>` のグラフ | **不可** (`Rc` は共有できない) |
| IR VM | 単一ヒープ + interpreter プロセス | 不可に近い |
| cranelift JIT | ネイティブコード | 可 |
| AOT | ネイティブコード | 可 |

tree-walker は `--check` と consistency harness の**オラクル**である。
ここで走らない意味論を入れると、その機能はオラクルを失う。したがって:

> **並行の構文は、逐次に実行しても同じ答えを出すものに限る。**

これは制約であると同時に、テスト戦略でもある (`toy test` の
`-j1` と並列で出力がバイト一致する、という既存の流儀と同じ考え方)。

### 2-c. ランタイムの下地は半分ある

- `toylang_rt` の `ThreadState` は **pthread_key TLS で per-thread 化済み**。
  出力シンク (`sink` / `err_sink`) と **allocator スタック**がここに居る
- **shadow stack は `static mut`** (`toy_shadow_stack` / `toy_shadow_depth`)。
  backtrace の土台なので、スレッドを入れるなら per-thread 化と
  codegen のアドレッシング変更が要る (ソースにその旨のコメントがある)
- ヒープは libc `malloc` なのでスレッド安全。ただし**確保カウンタ**
  (`__builtin_live_bytes` 等) はプロセス全体の数であり、per-thread に
  するか合算にするかは決めていない

### 2-d. allocator と region

`with allocator = arena { ... }` は lexical で、REGION 検査
([`REGIONS.md`](REGIONS.md)) が「スコープ付き allocator から出た値を
外へ出さない」を見ている。**arena を複数スレッドで共有すると、この検査の
前提 (単一の制御フロー) が崩れる。** 最初は「並列ブロックの中は default
allocator 固定」で閉じるのが安全である。

### 2-e. panic はプロセスを終える

言語の規約として例外は無く、`panic` は即時停止である
([`ERROR_MODEL.md`](ERROR_MODEL.md))。スレッドの panic を「join まで
運ぶ」形にすると、その規約に例外機構を持ち込むことになる。**並列ブロックの
中の panic はプロセスを終える**、が現行規約と一貫する。

## 3. 判定 (`Send` 相当) をいつ決めるか

[`EFFECT_SYSTEM.md`](EFFECT_SYSTEM.md) の「この先」は
**「region を跨がない値 = 送れる値」**という定義を挙げている。これは筋が
よいが、**先に決めるべきではない**。理由:

- 判定の良し悪しは「実際に書きたい並列プログラムが通るか」でしか測れない。
  今この言語で書かれた並列プログラムは 1 本も無い
- §4-A の形なら判定そのものが要らない。**要らない形で 1 回出荷し、
  そこで詰まった場所を見てから**判定を設計できる

## 4. 候補 (優先順位つき)

### ★★★ A. データ並列 — ハンドルもチャネルも無い fork-join

```rust
# 形は未決 (§5 の論点 1)。意味の側を先に決める。
par::for_range(0u64, segs.size(), fn (i: u64) -> () {
    # i 番目のセグメントを引く。書き込み先は i で分かれている
})
```

- **`Send` 判定が要らない。** 捕捉できるのはスカラーのコピーと窓
  (`Span<T>` / `Column<T>`) だけで、書き込み先が index で分かれていることは
  呼び出し側の責任 (`requires` で書ける)
- **逐次レーンで同じ答えになる。** tree-walker / IR VM はただのループに
  落とす。AOT / JIT は pthread
- **出力は禁止** (`Io` 効果をマスクする)。並列ブロックの中で `print` を
  許すと出力順が非決定になり、レーン間一致が崩れる。集めた結果を
  ブロックの外で出す形に倒す
- 実需要 (§1 の 4 つ) にそのまま効く

**入るもの**: 構文または stdlib 関数 1 つ、効果マスク 1 行、
`toylang_rt` のスレッド生成 (pthread)、shadow stack の per-thread 化、
consistency テスト (逐次と並列で同じ答え)。

### ★★ D. プロセス並列 — 共有メモリを持たない逃げ道

`io::spawn_process(path, args)` + パイプ。共有メモリが無いので `Send` も
move モデルの拡張も要らず、**全レーンで同じ挙動**になる。粒度は粗いが、
「12 セグメントを 4 プロセスで引く」には足りる。RUNTIME_LIBRARY が
「プロセス spawn は需要未確認」として保留しているものと同じ項目で、
A と排他ではない。

### ★★ B. `spawn` + join ハンドル (A の後)

todo.md が挙げている最小形。`Send` 相当の判定が要る (§3)。加えて
**逐次レーンでの意味が決まらない**のが難所である — spawn 時に即実行すると、
join 前の副作用の順が観測できる形でレーン間の答えが割れる。
A を出荷し、判定の材料が揃ってから。

### ★ C. チャネルとワーカープール (B の上)

デッドロック、ブロッキング、poller との統合が一度に来る。B が無ければ
書けない。

### ★ E. 現状維持 (イベントループのまま)

サーバに関してはこれが正解で、必要なのは §1 の穴 (容器から取り出した
ハンドルが閉じる / `from_fd` が無い) を塞ぐことだけ。
**並行性のタスクではない。**

## 5. 決めたこと (2026-09-20)

§4-A を採る。論点 1〜4 の答えと、その理由。

### 1. 形 — **構文**にする

```rust
parallel for i in 0u64..segs.size() {
    # i 番目のセグメントを引く。書き込み先は i で分かれている
}
```

stdlib 関数 (`par::for_range(from, to, f)`) は**書けない**。AOT の
クロージャが捕捉できるのはスカラーだけで (CLOSURE_CAPTURE)、§1 の
仕事はどれも窓か容器を要る — セグメントの一覧、出力の列。捕捉を
拡張してから関数形を入れるより、**本文をその場に置く**ほうが小さい:
本文は囲みの束縛をそのまま名指せて、それは今の `for` と同じである。

副産物が 2 つある。**逐次レーンはただの `for`** なので、意味論を
先に出荷して並列化を後から足せる (下の段取り)。そして**効果の
マスクを掛ける場所が構文の 1 点に決まる** — 関数形なら「渡された
クロージャ」を追う必要があった。

### 2. 並列度 — コア数、`TOY_PAR_THREADS` で上書き

`toy test` と同じ既定。**意味論ではない**ので言語仕様には書かない:
並列度は答えを変えてはならず、変えるなら本文が間違っている。

### 3. disjoint — **規約で守る**

型で守るには `Span::split_at` のような分割 API と、この構文のためだけの
別名規則が要る。窓は今も escape しか見ておらず (POINTER.md の既定)、
**規則を 2 つに分けない**。書き込み先が添字で分かれていることは
呼び出し側の責任で、`requires` に書ける。破れば競合するが、それは
`Span` を 2 本重ねたときと同じ性質の間違いである。

### 4. 逐次レーンの意味 — **完全逐次** (添字の昇順)

ラウンドロビンにすると「逐次でも同じ答え」の保証が弱くなる。
tree-walker と IR VM は `for` と 1 バイトも変わらない実行をする。
並列レーンは**順序を保証しない** — 本文が添字で分かれている限り
答えは同じで、分かれていなければどちらの順でも間違っている。

### 5. 確保カウンタ — 合算

per-thread にすると `--profile=mem` の数がスレッド数で割れて、
「このプログラムが何バイト持っているか」を答えなくなる。
**並列ブロックの中で `ensures allocates(N)` を書かない**ことを規約に
する (書けてしまうが、意味は「全スレッドの合計」になる)。

### 本文に許さないもの

- **出力** (`Io`) — 並べ替わった出力はレーン間一致を壊す。集めて
  ブロックの外で出す。`never_allocates` / `const fn` と同じ到達可能性
  検査で断る
- **`with allocator = ...`** — REGION 検査は単一の制御フローを前提に
  している (§2-d)。並列ブロックの中は default allocator 固定
- **panic はプロセスを終える** (§2-e)。join まで運ばない

## 6. 段取り

| | 中身 | 単独で出荷できるか |
|---|---|---|
| **A1** | 構文 + 検査 (Io / allocator) + **4 レーンとも逐次**で実行 | **可**。意味論と診断がここで固まり、以後の並列化は答えを変えられない |
| **A2** | `toylang_rt` に pthread、shadow stack の per-thread 化、AOT / JIT は本文を関数に切り出して分割実行 | A1 の後。逐次との一致を consistency で縛る |

A1 を先に出すのは、**並列化が最適化になる**ようにするためである。
「逐次と並列で答えが同じ」を後から確かめるのではなく、逐次の答えを
先に固定してから並列を足す。
