# SIMD — どこをベクトル化し、どこをしないか

> 前提: 仕様の正本は [`docs/language.md`](../../../docs/language.md) の「SIMD vectors」節、
> 言語側の設計と戦略は [`design-docs/SIMD.md`](../../../design-docs/SIMD.md)。
> ここは**このサービスのどの処理に効くか**だけを扱う。
> 実測はすべて 2026-09-03、AOT (`--release`)、aarch64 (Apple Silicon)。

## 1. 方針

**SIMD は「測って効いた場所にだけ」入れる。** 理由は 3 つ。

1. `u8x16` の走査はスカラー実装と**別のコード**になる。両方を持つとずれる
   余地が生まれるので、置く場所は少ないほどよい
2. ログサービスの時間はディスク I/O とアロケーション規律にも食われている。
   バイト走査が支配的でない場所を速くしても全体は動かない
3. **stdlib が既にベクトル化している**箇所を自前で書き直すのは、
   速くならないうえに保守先が増える

SIMD 版を入れる関数の規律:

- **スカラー参照実装を残す** (`_scalar` 接尾辞)。消さない
- **等価性をプロパティテストで縛る** (`--check`)。境界 (`len % 16`、
  非整列オフセット、空入力、200 ブロック超え) を必ず含める
- **4 レーンで同じ答えを返すことを pin する** (`assert_consistent`)
- **改善が誤差なら入れない** — スカラーに戻す

## 2. 使える面 (実測で確認した範囲)

| できること | 備考 |
|---|---|
| `u8x16` / `i32x4` / `i64x2` / `f32x4` / `f64x2` の 5 型 | **バイト処理は `u8x16` 一択**。128bit 固定 |
| 演算子が lane-wise、比較は**マスク** | `u8x16` の比較結果は `u8x16` (全 1 / 全 0) |
| **非整列ロードが動く** | オフセット 3 / 5 バイトで実測、インタプリタと AOT が一致 |
| `__simd_bitmask(v) -> u64` | **lane ごとの最上位ビット**を集める。`trailing_zeros()` / `popcount()` (`core/std/bits.t`) と組んで「どの lane か」「いくつか」を答える |
| `__simd_swizzle(a, idx)` | 値で引くバイト表引き (`pshufb` / `tbl`)。**index 16 以上は 0** |
| `__simd_shuffle(a, b, [k...])` | 定数マスクの置換。マスクはパース時に畳まれる |
| `__simd_bitcast` | 同じ 16 バイトを別の lane 型として見る。ビットは動かない |
| `__simd_any` / `__simd_all` / `__simd_select` / `__simd_reduce_*` | 畳み込みは lane 0→n の逐次と**仕様で固定** |
| `never_allocates unsafe fn` の中で使える | 取り込みの hot path に契約を掛けたままベクトル化できる (実測) |
| 4 レーンすべてが対応 | interpreter 自前 JIT だけ silent fallback (正しさは変わらない) |

### AOT のバイナリは可搬 (運用上重要)

AOT は `cranelift_native` ではなく `isa::lookup(Triple::host())` を使う
= **baseline ISA 固定**。128bit に留まる限り、ビルドしたマシンより古い
同アーキテクチャの CPU でも動く。**デーモンを 1 回ビルドして配る運用が
そのまま成立する**。256bit (Phase 4) に踏み込むと runtime dispatch が
要るので、そのとき初めてこの前提が変わる。

### まだ無いもの

| 無いもの | この設計への影響 |
|---|---|
| **`u16x8` / `u32x4` の lane 型** | バイトを**加算で**広げられない。`u8` lane の累積は 255 で wrap するので畳む規律が要る (§3 P2)。`bitcast` は再解釈であって拡張ではない |
| **carry-less multiply** | **CRC-32 はベクトル化できない**。スカラーの slice-by-4/8 テーブルで書く |
| gather / scatter | 転置リストの間接参照は効かない |
| 実行時の幅検出 / 256bit | 幅はソースに書く値。**幅を名指しするのは `src/simd_bytes.t` の中だけ**にして、Phase 4 が来たときの書き換えを局所に閉じる |
| 実行時 lane index (`__simd_extract`) | リテラルのみ。`bitmask` + `trailing_zeros` で代替できるので実害は消えた |

## 3. この設計で使う 4 つの型 (パターン)

すべてインタプリタと AOT で同じ答えを返すことを実測済み。

### P1. ブロック内の最初の一致位置 — `bitmask` + `trailing_zeros`

```rust
# The first lane where `block` equals `needle`, or 16 if there is none.
# The `any` gate stays: it is one instruction on both ISAs, while the
# bitmask is a several-instruction sequence on NEON, so the cheap
# question goes first and the precise one only on a hit.
unsafe fn first_hit(p: ptr, i: u64, needle: u8) -> u64 {
    val block: u8x16 = __simd_load(p, i)
    val want: u8x16 = __simd_splat(needle)
    val eq = block == want
    if !__simd_any(eq) { return 16u64 }
    __simd_bitmask(eq).trailing_zeros() as u64
}
```

**`__simd_bitmask` が集めるのは lane の最上位ビット**であって「非ゼロか」
ではない。比較が返すマスク (全 1 / 全 0) に対しては両者が一致するので
問題にならないが、**比較の結果以外に bitmask を掛けるときは要注意**。

> 初版はこの位置を `__simd_reduce_min(__simd_select(mask, idx, splat(255)))`
> で求めていた (`bitmask` が無かったため)。同じ答えを出すが、定数
> インデックスベクタを持ち回る必要があり、`bitmask` 版の方が短い。
> **この設計から消した。**

### P2. 一致数のカウント — lane 累積が最速

```rust
acc = acc + ((block == want) & one)     # one = splat(1u8)
# every 200 blocks (u8 lanes wrap at 255, they do not saturate):
total = total + (__simd_reduce_add(acc) as u64)
acc = zero
```

`__simd_bitmask(eq).popcount()` でも書けて、**畳む規律が要らないぶん
安全**だが、実測では **lane 累積の方が約 11% 速い** (§5)。行数カウントは
取り込みの内側なので、ここだけは速い方を採り、200 ブロック境界を
テストで踏む。

### P3. 分岐なしのバイト変換

```rust
val isupper = (block >= splat_A) & (block <= splat_Z)
val out = __simd_select(isupper, block | splat_20, block)
```

`u8` lane の比較は符号なしなので、ASCII の範囲判定がそのまま書ける。
**`String::to_lower` は stdlib が既にこれをやっている** ので、
`String` を持っている場面では自前で書かない (§4)。

### P4. 分類は表引き — `swizzle`

トークン化の「語を構成する文字か」は、範囲比較を 4 本並べるより
**nibble 表引き 1 組**が短い。`__simd_swizzle` は値で引けるので、
16 エントリの表 2 枚 (下位 nibble 用と上位 nibble 用) を AND する
古典的な形がそのまま書ける。

```rust
# lo[b & 15] & hi[b >> 4] != 0  <=>  b is a word byte
val lo = __simd_swizzle(lo_table, block & splat_15)
val hi = __simd_swizzle(hi_table, block >> 4u64)
val is_word = (lo & hi) != zero
```

表は起動時に 1 回作る。**`__simd_swizzle` は index 16 以上で 0 を返す**
ので、範囲外の扱いを別に書かなくてよい。

### P6. 重なり窓をまとめて作る — `swizzle` + `bitcast`

ローリングハッシュのように「1 バイトずつずれた窓」がほしいとき、
`__simd_swizzle` の添字表に重なりを書けば 1 回のロードで 4 窓が取れる。

```rust
# idx = [0,1,2,3, 1,2,3,4, 2,3,4,5, 3,4,5,6]
val block: u8x16 = __simd_load(p, at)
val gathered = __simd_swizzle(block, idx)
val words: i32x4 = __simd_bitcast(gathered)   # 4 つの u32 窓
```

**`i32x4` の `>>` は算術シフト**である (lane が符号付きで、`>>` は 1 つ
しかない)。ハッシュのように**下位ビットだけを使う**なら害は無い —
符号拡張はマスクより上のビットにしか届かない。上位ビットを使う用途では
`bitcast` で別の見方に移すか、スカラーに落とす。

### P5. 16 バイトの一致判定

LZ77 のマッチ延長。`__simd_all(a == b)` で 16 バイト進め、外れたら
`bitmask(a == b).trailing_zeros()` で**一致した長さがそのまま出る**
(初版は「スカラーの末尾処理」と書いていたが、これも bitmask で消える)。

## 4. 先に問うべきこと — stdlib は既に SIMD 化されている

戦略 B (Phase 3) で、**stdlib のバイト kernel は置換済み**である。
言語側の実測 (4096 バイト、AOT、aarch64):

| kernel | scalar | SIMD | |
|---|---|---|---|
| `String::eq` / `Vec<u8>::eq` | 0.26s | 0.02s | 13x |
| `to_upper` / `to_lower` | 1.38s | 0.08s | 17x |
| `contains` (先頭バイトが稀) | 1.93s | 0.12s | 16x |
| `contains` (先頭バイトが密) | 0.43s | 0.28s | **1.5x** |
| `split` | 0.93s | 0.63s | 1.5x |

この表から、この設計が受け取るべき教訓は 3 つ。

1. **`String` / `Vec<u8>` を持っている場面では自前で書かない。**
   等値比較・大小変換・部分一致は既にベクトル化されている
2. **`contains` は入力で 10 倍変わる。** skip が効くのは「先頭バイトが
   稀」なときだけ。ログ本文で `e` や `t` を先頭に持つ語を探すのは
   **密な側**であり、stdlib の形のままでは 1.5x に落ちる。
   → この設計は**先頭 + 末尾の 2 バイトでマスクを取る** (§3 の応用)。
   候補の密度が積で落ちるので、密な先頭バイトでも崩れない
3. **`split` の 1.5x は走査ではなく確保が原因**。part ごとに
   `substring` が確保する。**[`MEMORY.md`](MEMORY.md) の規律
   (リクエストごとに確保しない) は、そのまま速度の話でもある**

### それでも自前で書く理由

`contains` の走査を `src/simd_bytes.t` に持つのは、**`String` を作れない**
から。フレームを展開したアリーナは `Vec<u8>` の中の**部分区間**であり、
`String` に切り出すと 1 フレームごとに確保が走る。窓 (`Span<u8>`) の上で
走査する API が要る、というのがこの設計の一次的な動機で、
「stdlib が遅いから」ではない。

## 5. 実測

**測り方**: `time::now_mono_ns()` を**プログラムの中で**読み、16 MiB の
バッファを 1 回走査する時間を 5 回のうちの最小値で取る (ウォームアップ 1 回
は捨てる)。AOT `--release`。外部の `time(1)` で N を振って傾きを取る旧法とも
±2% で一致した (27.7ms → 27.3ms) ので、以下は**内部計測の値**を載せる。

### 改行の走査とカウント (S1 相当)

| 実装 | 1 パス (16 MiB) | スループット | 対スカラー |
|---|---|---|---|
| スカラー (`v.get(i)` のループ) | 27.3 ms | 615 MB/s | 1x |
| `u8x16` + lane 累積 (P2) | **1.04 ms** | 16.1 GB/s | **26x** |
| `u8x16` + `bitmask.popcount()` | 1.17 ms | 14.4 GB/s | 23x |

**カウントは lane 累積が 12% 速い。** 代わりに 200 ブロックごとに畳む規律が
要る (§3 P2)。

### 部分一致検索 (S2 相当、16 MiB、一致なし)

**候補が疎な場合** (11 バイトの語、先頭+末尾の組が現れない):

| 実装 | 1 パス | スループット | 対スカラー |
|---|---|---|---|
| スカラー (先頭バイトで絞る素朴版) | 37.2 ms | 451 MB/s | 1x |
| 先頭+末尾マスク + ブロック再走査 | 2.52 ms | 6.7 GB/s | **15x** |
| 先頭+末尾マスク + `bitmask` 反復 | 2.46 ms | 6.8 GB/s | 15x |

**候補が密な場合** (3 バイトの語、先頭+末尾の組が 23 バイトごとに現れ、
検証は必ず失敗する):

| 実装 | 1 パス | スループット | 対スカラー |
|---|---|---|---|
| スカラー | 37.2 ms | 451 MB/s | 1x |
| 先頭+末尾マスク + **ブロック再走査** | 29.1 ms | 577 MB/s | **1.3x** |
| 先頭+末尾マスク + **`bitmask` 反復** | **9.2 ms** | 1.8 GB/s | **4.0x** |

**これが `__simd_bitmask` が入った理由そのもの**である。候補が出た瞬間に
16 バイトを舐め直す形は、候補が密になると 1.3x まで落ちる — 言語側が
stdlib の `contains` で観測した「稀なら 16x、密なら 1.5x」と同じ現象を、
こちらでも再現した。**`bitmask` で候補 lane だけを反復すると 3.2 倍速い。**

この設計への帰結は 2 つ:

1. **候補の反復は必ず `bitmask` で書く。** ブロック再走査は書かない
2. 先頭+末尾の 2 バイトフィルタは、候補密度を積で落とすので**疎な側に
   寄せる効果**がある。両方を併せて初めて、入力に依らず速い

### 圧縮と展開 (S4 / S5、`src/lsz.t`)

同じ入力・同じフラグ (AOT `--release`) で、段階ごとに差し替えて測った
(kern.log、7.4 MB、7 回の最小値):

| 実装 | 圧縮 | 展開 |
|---|---|---|
| スカラー | 33 ms | 33 ms |
| + マッチ延長と 16 バイトコピー (`u8x16`) | 22 ms (1.5x) | **11 ms (3.0x)** |
| + ハッシュの 4 位置バッチ (`swizzle` / `bitcast` / `i32x4`) | **19 ms (1.7x)** | — |

**ハッシュのバッチ化は 22 → 19 ms**。7 回すべて 19 ms で、ばらつきは
無かった (スカラー側も 22〜23 ms に収まる)。1 回の 16 バイトロードから
`__simd_swizzle` で **重なった 4 窓** (0..3 / 1..4 / 2..5 / 3..6) を集め、
`__simd_bitcast` で `i32x4` として読み、1 回の乗算とシフトで 4 つの
ハッシュを得る — スカラー版が 16 回のバイトロードと 4 回の乗算で
出していたものと**同じ値**である。

効きが 1.16x に留まるのは、ハッシュが圧縮の一部でしかないため。
表引き・表更新・候補の検証は 1 位置ずつのままで、**gather / scatter が
無い以上そこは並べられない** (SIMD.md §2 の「無いもの」)。

**圧縮後のバイト列は完全に一致する** (1,211,553 バイト) — SIMD 版の
マッチ延長がスカラー版と同じ判断をしている証拠で、これが入れてよいかの
第一条件だった。等価性は `match_len` と `match_len_scalar` を実ログ 4 本の
118 万箇所で突き合わせて 0 不一致を確認してある。

**展開の 3.0x に対し圧縮が 1.4x** なのは仕事の内訳が違うから。展開は
ほぼコピーだけなのでブロック化がそのまま効く。圧縮はハッシュ計算と
1 バイトずつの前進が支配的で、マッチ延長はその一部でしかない
(ログのマッチは短く、実測で 16〜36 バイト級)。**圧縮側をさらに速く
するなら、次に手を入れるのは延長ではなくハッシュと走査**である。

### この数字の読み方

- 比較対象は**素直に書いた toylang のスカラーコード**であって最適な C ではない。
  26x のうち相当部分は「1 バイトごとに `Vec::get` を呼ぶのをやめた」効果
- 16 MiB は L2/L3 に収まる。**ディスクから読んだ直後の実データでは
  メモリ帯域が上限**になるので、16 GB/s は上限値であって運用値ではない
- 効くのは走査が支配的な処理だけ。取り込み全体ではパース・辞書引き・
  バッファ書き込みが残る。**S3 (トークン化) まで入れて初めて
  取り込みの CPU が動く**

## 6. どこに効かせるか

| # | 場所 | 何をするか | 効き |
|---|---|---|---|
| S1 | **取り込みの行分割** | `\n` の位置 (P1) と行数 (P2) | 実測 **26x** |
| S2 | **クエリの `contains`** | 先頭+末尾の 2 マスク → `bitmask` で候補反復 → 検証 | 実測 **15x** (候補が密でも **4x**) |
| S3 | **トークン化** | 語区切りの分類 (P4 の表引き) と小文字化 (P3) | 未測。取り込みの CPU の主 |
| S4 | **LSZ1 の圧縮** | マッチ延長 (P5)、リテラルの 16 バイトコピー、**ハッシュの 4 位置バッチ** (P6) | 実測 **1.7x** |
| S5 | **LSZ1 の展開** | 16 バイトコピー。**offset < 16 の重なりマッチは除外** | 実測 **3.0x** |
| S6 | **JSON エスケープ走査** | 要エスケープバイトが無いブロックは丸ごとコピー | 未測 |
| S7 | ラベルの走査 | `=` と空白の位置 (P1) | 行が短く効きは小さい |

### やらない

| 場所 | なぜ |
|---|---|
| **CRC-32** | carry-less multiply が無い。**構造的に無理**なのでスカラーのテーブル方式で書く |
| **varint のデコード** | `shuffle` / `swizzle` は入ったが、**可変長の詰め替えは分岐が本体**で、16 バイト単位に割れない。スカラーのまま |
| **転置リストの交差** | 間接参照が主。`i32x4` の 4 lane では割に合わない |
| **時刻範囲フィルタ** | 直前の varint 復号がスカラーなので、そこが上限になる |
| **チェックサムの別方式化** | `bitcast` + `swizzle` で総和を作れなくはないが、4 バイト単位に落ちて `u8` 累積より遅い。**`u16x8` / `u32x4` が入ったら再検討** |
| **hex / base64 の自前実装** | `core/std/hex.t` / `base64.t` が既にあり、`swizzle` の表引きで書かれている。**使う側に回る** |

## 7. 自動ベクトル化 (戦略 C) を待つ形で書く

言語側は**限定的な自動ベクトル化**を計画している (Phase 4、未着手)。
認識される条件は 4 つで、いずれも既存の機構で判定できるものだけ:

```
soa 配列 + `for i in 0..n` の range ループ
  + guard がゼロ (GUARD-ELISION 済み)
  + body が pure (EffectSet が EMPTY)
  + ループ跨ぎ依存なし
```

**この 4 条件は、レコード表の列走査がまさに満たせる形である。**
[`STORAGE_FORMAT.md`](STORAGE_FORMAT.md) §4 で record table を SoA
(列ごと) にしたのは圧縮とキャッシュのためだったが、**同じ配置が
将来の自動ベクトル化の入口にもなる**。今日やっておくべきことは:

1. 列の走査を `for i in 0u64..n` の range ループで書く (`while` にしない)
2. 添字の guard を `requires` かループ範囲で落とせる形にする
   ([`design-docs/GUARD_ELISION.md`](../../../design-docs/GUARD_ELISION.md))
3. 走査 body に呼び出し・`print`・確保を混ぜない (pure に保つ)

これらは**今日の性能にも効く** (guard が消える) ので、投機的な作業には
ならない。Phase 4 が来たら `--simd-report` (戦略 D) が
「なぜベクトル化されなかったか」を名指しで返すので、そのときに詰める。

## 8. 実装上の落とし穴 (実測で踏んだもの)

| 落とし穴 | 対処 |
|---|---|
| `acc = __simd_splat(0u8)` が `[E0010]` — 代入位置には型注釈が無く lane 型が決まらない | `val zero: u8x16 = __simd_splat(0u8)` を先に束縛して `acc = zero`。`__simd_load` / `__simd_bitcast` も同じ |
| `__simd_load` / `__simd_store` は `unsafe fn` の中でしか呼べない (`[E0024]`) | SIMD は `src/simd_bytes.t` に閉じ込める。**呼び出し側は safe のまま** |
| `__simd_bitmask` は「最上位ビット」を集める (「非ゼロか」ではない) | 比較マスク以外に掛けない。float lane では符号ビットになる |
| `bitmask` の前に `__simd_any` を外すと NEON で遅くなる | **ゲートを残す** (仕様書が明示している) |
| `u8` lane の累積は 255 で wrap する (飽和しない) | P2 の「200 ブロックごとに畳む」。境界をテストで踏む |
| 整数の `/` と `%` は型エラー | `& 15u64` / `>> 4u64` に置き換える |
| インタプリタ自前 JIT は SIMD で silent fallback | **ベンチは必ず AOT で**。インタプリタは正しさのオラクル |
| マスクは `bool` ではない | `if mask` とは書けない。`__simd_any` / `__simd_all` を通す |
| IR VM の slot が 16 バイトに広がっている | ベクトルを使わないコードにも典型 2〜3% の税。**こちらが選べるものではない**ので、インタプリタのベンチ値を絶対視しない |
